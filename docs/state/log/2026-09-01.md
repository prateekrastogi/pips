### The perturbation is a mirror, not a shift — and a mutation taught me why

My first version added a constant to every post-decision bar. Six of six mutations died, so it
looked finished. But one of them — perturbing *every* bar, visible ones included — left the
causal rule invariant, which it should not have. The reason: **an additive shift moves every

## M18 — PSR and the Deflated Sharpe Ratio

**Red first**: `ModuleNotFoundError: No module named 'pips.validation.deflated_sharpe'`.

The falsifier work has run to the edge of what data exists, so this tick opened M18 — pure
statistics, no data required. §6 M18 names one trap in its own text: *"kurtosis convention: γ₄
raw; excess+... guard in code"*, and it is worth being precise about why that is the thing it
singles out.

The PSR denominator contains `(γ₄ - 1)/4 · SR²`. A normal series has **raw** kurtosis 3;
almost every library returns **excess** kurtosis, which is 0 for the same series. Substitute 0
for 3 and the denominator shrinks, the statistic inflates, and the PSR comes out **higher** — a
better-looking result produced by a units mistake, with nothing in the output to show for it.

So the guard is mathematical rather than heuristic: **γ₄ ≥ 1 + γ₃²** for every distribution
possessing the moments, so a value below that bound is not a raw kurtosis at all. The bound
moves with the skew because the mathematics does — a flat "must be ≥ 3" would reject genuinely
skewed data, and there is a test for exactly that (skew 2 admits 5.1 and refuses 4.9).

`normal_ppf` inverts by bisection rather than a rational approximation: deterministic to the
last bit on every machine (rule 1), where an approximation carries its own error profile into
every DSR computed from it.

### My golden was wrong and the code was right

I asserted that with γ₃ = 0 and γ₄ = 3 the denominator is 1, i.e. PSR = Φ(SR·√(n−1)). It is
not: substituting γ₄ = 3 leaves `(γ₄ - 1)/4 · SR² = SR²/2`, which is exactly **Lo's (2002)
variance** for the Sharpe estimator. The denominator could only be 1 at γ₄ = 1, which no real
distribution has. Pinning the correct reduction is worth more than the wrong one would have
been — it now fixes both the kurtosis coefficient and the (n−1) scaling.

### Monotonicity could not see a sign error

Replacing `Φ⁻¹(1 - 1/N)` with `Φ⁻¹(1/N)` flips that term's sign, but the second term is large
enough that the **sum still increases with N** — so the ordering test passed while the value
was 0.64 instead of 3.26. A mutation showed it.

The fix is a bound from theory rather than from my own output: the maximum of N standard
normals concentrates just below `√(2 ln N)`, with the Gumbel correction accounting for the gap.
Asserting `0.7·√(2 ln N) < E[max] < √(2 ln N)` checks the formula rather than merely pinning
it, and exact goldens sit alongside to detect any change at all.

```
N=    2  E[max SR]=0.519755   sqrt(2 ln N)=1.1774
N=   10  E[max SR]=1.574598   sqrt(2 ln N)=2.1460
N=  100  E[max SR]=2.530603   sqrt(2 ln N)=3.0349
N= 1000  E[max SR]=3.255122   sqrt(2 ln N)=3.7169
```

## M18 — CSCV / PBO, and a directional claim I withdrew

**Red first**: `ModuleNotFoundError: No module named 'pips.validation.pbo'`.

CSCV asks what no in-sample number can: **when I pick the best config on half the data, how
often is it below median on the other half?** Around half the time means the selection
procedure is choosing noise — and it says so without being told which config is really good,
which makes it a check on the PROCEDURE rather than on a result.

```
pure noise      PBO 0.750   (8 configs, 20 splits)
one real edge   PBO 0.000   (WINNER selected in all 20)
```

All C(S, S/2) combinations are evaluated, never a sample: the "combinatorially symmetric" in
the name IS the method, and sampling produces a different estimator with a different variance.

### I withdrew a claim my own experiments contradicted

My docstring asserted that boundary leakage biases PBO **downward**, toward declaring the
procedure sound — a plausible story: the IS winner looks good OOS because they share bars.

It does not reproduce. On noise, purging took PBO from 0.750 to 0.150. So I built a fixture
with genuinely overlapping labels (h-bar sums, so adjacent observations share bars) and it went
the same way, 0.900 to 0.800. Removing data also adds estimation noise, and which effect
dominates is not something these experiments settle.

Rather than keep a directional assertion the tests contradict, **the claim is withdrawn** and
what the purge actually guarantees is asserted instead: after purging, no in-sample
observation's label window reaches into an out-of-sample block. That is structural, exact, and
checkable — with a control showing that without the purge, labels *do* reach across.

### Two survivors, and a third mistake of my own

- **Purging every boundary rather than only crossing ones** survived: it is wasteful but the

## M18 — stationary bootstrap

**Red first**: `ModuleNotFoundError: No module named 'pips.validation.bootstrap'`.

A bootstrap that resamples single observations destroys serial dependence — and serial
dependence is most of what makes a return series hard. Resample it away and every confidence
interval comes out too narrow, which is to say every result looks more significant than it is.
Not a crash: a number that is confidently wrong in the flattering direction.

Dependence recovery scales with the block length exactly as theory says it should, and the
monotone relationship is asserted rather than a single threshold — a `> 0.5` check passes for
an implementation whose block length does nothing:

```
original AR(1) lag-1 autocorrelation   0.827
  mean block   1   -> -0.008    (the IID bootstrap; dependence destroyed)
  mean block   5   ->  0.649
  mean block  20   ->  0.782
  mean block  50   ->  0.804
```

**The test that matters is the one an IID bootstrap fails.** Everything structural — right
length, valid indices, reproducible under a seed — is equally true of resampling single
observations. A suite that never measures whether dependence SURVIVED passes for the bootstrap
this one exists to replace.

### Three survivors, and the last one is the worst

- **No wrapping** survived because my assertion had an escape clause: `wrapped or indices[0]
  != 0` is true for nine starts in ten. Replaced with a decisive one — with a mean block of
  10,000 the walk is unbroken, and on a circle that visits every index exactly once whatever
  the start. Clamped at the end it would stall and repeat.
- **The global RNG** was caught (a bootstrap reading `random.random()` is reproducible only
  until something else in the process draws a number).
- **Every resample in a call deriving from the same seed** survived, and it is the worst of
  the three: N identical resamples give a **zero-width confidence interval** — the most
  extreme version of the exact failure this module exists to prevent. Neither "same seed
  reproduces" nor "different seeds differ" catches it, because both are true of that
  implementation. It needed a test asserting the resamples within one call differ.

**Mutation run — 3 of 6, then 6 of 6.**

## M18 — Hansen's SPA, and the demonstration that makes it worth having

**Red first**: `ModuleNotFoundError: No module named 'pips.validation.spa'`.

SPA asks whether the BEST model in a set genuinely beats a benchmark, given that you looked at
all of them. White's Reality Check answers the same question too conservatively, and the reason
IS the content of "Hansen recentering":

**The Reality Check lets hopeless models inflate the null.** It recenters every model on its own
sample mean, so a model that lost badly still contributes a draw to the maximum. Add enough
irrelevant bad models and the null's maximum drifts up, the p-value rises, and a genuinely
superior model stops being detectable — **you fail to reject because of models nobody would
ever have traded.**

Both recenterings are implemented, deliberately: the claim is only worth making if the
alternative can be run beside it. Padding a marginal-but-significant result with twelve
untradeable models:

```
                lean      padded
  Hansen SPA    0.040  ->  0.040     unchanged
  Reality Check 0.040  ->  0.128     crosses 0.05 — significant becomes not
```

That crossing is the whole argument, and it needed a **marginal** edge to show at all. With a
large edge the statistic outruns anything the bootstrap produces, both recenterings return
p = 0, and the comparison shows nothing. The interesting behaviour lives where a result is
close to its threshold — which is where it lives in practice.

### My "noise" was not noise

The first fixtures used `(t * 7) % 21`. Seven divides twenty-one, so the sequence cycles
through **three values**, and the "zero-mean noise" had a mean of +0.003 with a t-statistic of
7.5. The noise-only control passed for entirely the wrong reason. Coprime multipliers (37, 101)
give means around 2e-5.

That is the sixth time this session a modular fixture has been degenerate, and the pattern is
specific enough to name: **`(a·t) % m` cycles through only `m / gcd(a, m)` values.** Choosing
`a` and `m` coprime is not a stylistic preference.

### Two survivors, each needing a fixture aimed at it

- **Replacing √(2 log log n) with a constant** survived because every model was far outside
  both candidate thresholds. Hansen's threshold at n = 200 is −1.826 standard errors; a
  borderline model at −1.4 is inside it and must survive, while a constant of 1.0 would zero
  it. The rate comes from the law of the iterated logarithm, which is why it shrinks correctly
  with n rather than being a number somebody picked.
- **Removing the `max(0, ·)` floor** survived because both versions give a large p-value. The
  floor is definitional: when nothing beats the benchmark, the evidence against "nothing beats
  the benchmark" is exactly nothing, and the statistic is 0 — not the least-bad model's
  negative t.

**Mutation run — 6 of 8, then 8 of 8.**

CI green: 975 passed.

## M18 — Romano-Wolf stepdown

**Red first**: `ModuleNotFoundError: No module named 'pips.validation.romano_wolf'`.

The last gate before a config is called a survivor. Bonferroni answers the same question by
dividing alpha by the number of tests — correct, and wasteful: it ignores that the statistics
are correlated, which a family of alphas over one universe certainly is. Romano-Wolf uses the
bootstrap joint distribution, so correlation is accounted for rather than assumed away.

**The stepdown is where the power comes from**, and it is demonstrated rather than asserted —
the single-step version is implemented alongside, for the same reason the Reality Check sits
beside SPA:

```
thresholds   1.0036  ->  0.9241  ->  0.8260
  'borderline' has statistic 0.944: single-step cannot reach it at 1.004;
  after 'strong' and 'medium' fall the bar drops to 0.924 and it does.
```

Bootstrap draws are computed **once** and reused across rounds. Regenerating per round would
add sampling noise between steps, so a later threshold could rise and the guarantee that
stepping down never rejects fewer would quietly stop holding — for a reason unrelated to the
procedure.

The Monte-Carlo size test §6 M18 asks for is here too, and states its own limits: forty
replications cannot pin 0.10 precisely, so it asserts the family-wise rate is far below the
~0.41 that uncontrolled per-hypothesis testing would give on five models. That is what
separates a procedure controlling FWER from one that does not, and it is paired with a power
control — FWER control is otherwise achieved trivially by rejecting nothing.

### An infinite loop, and the third harness failure

The mutation removing `surviving -= newly` did not fail — it **hung**, and took a ten-minute
mutation batch with it. Termination was true but implicit: each round either rejects one
hypothesis or breaks, so the count cannot exceed the family size. That is now a written bound,
and the same mutation fails in a second. **A procedure that cannot terminate is not a
procedure**, and the guarantee belongs in the code rather than in my head.

Trying to work around the hang, I reached for `timeout 90 uv run pytest` — and `timeout` is not
on macOS. Every probe silently produced nothing and I read five blank results as five
survivors. That is the **third** harness failure this session (stale bytecode, a silent batch,
and now a missing binary), all in the same direction: **reporting nothing as reporting fine.**
The bound in the code removed the need for the workaround entirely, which is the better fix.

**Mutation run — 6 of 6** once the loop could fail instead of hang.

- The borderline fixture had a statistic of 1.692, above the very first threshold, so the

## M18 — sealed lockbox, enforced in the data layer

**Red first**: `ModuleNotFoundError: No module named 'pips.data.lockbox'`.

M11 built the ledger half: every unlock attempt recorded, append-only, a second attempt voiding
the cycle. That records what happened. It does not stop it.

This is the other half — **the data layer refuses to hand over the bytes.** A holdout that is
merely a convention is a holdout that gets read: not maliciously, but by a loop that widens its
date range by a month, or a notebook that asks for "everything". The only holdout that survives
contact with a research process is one that cannot be fetched.

### What refusal looks like is the design decision

**It raises. It does not filter.** Silently returning the portion outside the holdout is the
worst option available: the caller computes a perfectly valid-looking result over a window it
did not choose, with a shorter series as its only clue — and a shorter series is not an error
message. Same failure as a rate-limited HTTP 200 recorded as "no data", arriving at the one
place this project has agreed not to look. There is deliberately no "give me what you can"
path, and a test asserts none exists for a caller to find.

**Every attempt that touches the holdout is recorded**, refused ones included and *before* the
raise so it cannot be skipped. Requests that never touch it are not recorded — logging every
ordinary read would bury the ones that matter.

**An unknown stage is refused**, and so is an unknown release stage at construction. A stage
nobody recognises is not evidence of authority to read sealed data.

The stage ordering comes from `registry.STAGE_RANKS` rather than a second copy: two
hand-maintained orderings drift, and a lockbox that thinks S5 outranks S6 opens early with
nothing else noticing.

### And it is wired where it can actually bite

A check nothing consults is a dead check — the lesson from `check_unexplained_ratio_jump`,
written at M5, unit-tested, and never called by the runner for a whole milestone. So the
lockbox is checked in `load_panel`, at the read, with tests that a guarded read of the June
fixtures is refused at S1 and permitted at S6.

`lockbox=None` means no holdout has been DECLARED, which is different from a holdout that
permits everything, and the default must not quietly become the latter. A lockbox supplied
*without* a stage is refused outright: whichever default were chosen would be wrong — a
permissive one opens the box, a restrictive one blocks every ordinary read until someone
"fixes" it by passing the permissive value everywhere. That guard survived its first mutation
run and now has a test.

## M18 — hierarchical partial pooling for family means (the last M18 item)

**Red first**: `ModuleNotFoundError: No module named 'pips.validation.partial_pooling'`, then
`... 'pips.validation.family_pooling'`.

Nine alpha families, each with a handful of configs, and the question is what F5's mean
performance actually is. **No pooling** — each family's own sample mean — is mostly noise on
small samples, and the best-looking family is then the luckiest one: §3.6's multiplicity
problem wearing a new hat. **Complete pooling** — one grand mean — discards every real
difference, which is the reason the taxonomy exists. Partial pooling asks how much of the
observed spread is REAL and moves each family toward the centre by exactly that much. Same
estimator as A12's slot shrinkage, one level up.

### The trap is a negative variance estimate

`tau^2` comes from method of moments — the observed spread of family means minus what
within-family noise alone would produce — and that subtraction goes NEGATIVE whenever the
families really are alike. A negative `tau^2` yields a negative weight, and a negative weight
pushes each family AWAY from the grand mean. Anti-shrinkage: the exact inverse of the intended
correction, arrived at silently, producing a spread wider than the data supports. It looks like
a stronger result. Floored at zero, which is complete pooling — the right answer when nothing
separates them. **Both** the floored and the raw estimate are reported: a run that floored is a
finding about the taxonomy, not an arithmetic detail, and should not have to be inferred from
all the weights being zero.

The fixture that exercises the floor is built so the negative is guaranteed rather than reached
near a boundary — each family a PERMUTATION of one shared value set, so family means are
exactly equal while within-family variance stays large, giving `0 - sigma^2/n` strictly below
zero. My first attempt used the modular-noise helper at n=6 and landed within a few percent of
the boundary, where it could have flipped sign on any change to the helper.

**The centre is the unweighted mean of family means.** Weighting it by sample size would let
the largest family dominate the target every smaller family is shrunk toward, which is the path
by which one big family's luck becomes contagious.

### Six of my eleven tests were satisfiable by a wrong implementation

The first mutation run: `shrink-swapped`, `dof-off-by-one`, `spread-divisor`, `grand-weighted`,
`no-zero-guard` and `noise-share-max` all survived. Not one of them asserts something false —
they assert RELATIONSHIPS (this weight is smaller, this ordering holds, this lies between those
two), and relationships constrain the shape of the answer without constraining the answer.
`shrink-swapped` is the clearest: swapping `weight` and `1-weight` is still a convex
combination, so it stays between the two means and preserves the ordering, and every relational
test passes while every number is wrong. `grand-weighted` broke the one design decision the
docstring argues for, and nothing noticed.

Fixed by adding exact hand-computed cases — two families, four numbers, every intermediate
checkable by hand — plus an UNBALANCED case, since `sigma^2/n_j` differs between families only
when their sample sizes do, and every balanced fixture is blind to how those terms combine.

## M19 — non-dominated (Pareto) sort `[C-SEL-01]`

**Red first**: `ModuleNotFoundError: No module named 'pips.selection.pareto'`.

M19 selects across net return, DSR, MDD/CVaR, cost share, turnover/order count and stability.
Those do not reduce to one number, and inventing weights to make them reduce is how a search
ends up picking whatever the weights favoured rather than whatever the evidence supports. The
Pareto sort answers the question that CAN be answered without weights — which candidates is
nothing strictly better than — and leaves the trade-off to a decision someone makes out loud.

Salvage swept first (rule 13, though a sort is not one of the enumerated component types): the
only `../past` hit is `convexity`'s `band_calibration.py`, which reports a cost/tracking
frontier from a parameter sweep and contains no dominance test. No donor.

### The direction of each objective is the whole risk

Return is maximised; drawdown, cost and turnover are minimised. One objective pointed the wrong
way silently inverts part of the frontier while still producing a frontier — right shape, wrong
members, nothing in the output to say so. So direction is DECLARED on the objective and never
inferred from the name: `max_drawdown` and `neg_drawdown` are equally plausible conventions and
only the caller knows which one a metric follows. The flip happens once, in `_value`, which
orients every axis so larger is better; the dominance test then contains no direction logic at
all, so there is no second place for a sign to go wrong.

Two tests exist purely to prove direction is CONSULTED, because a sort that ignores it still
returns a plausible frontier: flipping one objective's direction must flip the verdict, and
minimising a value must give the same fronts as maximising its negation.

### Three refusals, each producing a confident well-formed meaningless answer

- **No objectives.** Nothing dominates anything, so the frontier is the entire population —
  a full result, not an empty one, reading as though every candidate survived on merit.
- **A non-finite objective.** Every comparison with NaN is false, so a NaN candidate is
  dominated by nothing and lands on the FIRST front: a broken measurement reported as a winner.
- **A missing metric.** Defaulting it ranks the candidate wherever that value falls, which for
  a minimised metric is the best score available.

And dominance needs BOTH clauses — at least as good everywhere, strictly better somewhere.
Drop the second and every candidate dominates its own twin, so tied pairs eliminate each other
and the frontier loses exactly the results that reproduced.

### A redundant guard is not a second line of defence

I first wrote the layering as `while remaining` with an `if not front: raise` guard, then added
a bounded loop and a terminal check as belt-and-braces. The mutation run said what that was
worth: with both present, removing EITHER left the other raising the same error, so
`no-stall-guard`, `unbounded-loop` and `no-terminal-check` all **survived** — three mutations
no test could tell apart. Redundant defence that nothing can observe is dead code wearing a
safety label.

Kept the bound alone. It is the better of the two: each front removes at least one candidate,
so there can be at most one front per candidate, and with only that mechanism removing the
terminal check is caught CLEANLY by the existing partition invariant (candidates go unplaced),
while removing the bound itself hangs — which is the correct signal that the bound is what
stops the stall. Romano–Wolf's unbounded loop hung a ten-minute batch; a stall reports nothing
at all, which is worse than reporting a failure.

**Mutation run: 15 of 15** (12 clean, plus the three stall mutations re-checked after the
restructure).

## M19 — the turnover calculus: Faustmann h* and selectivity tau* `[C-TURN-01]`

**Red first**: `ModuleNotFoundError: No module named 'pips.selection.turnover'`.

Quantitative Foundations §6.1-§6.2, consulted by section. Both are C2 rules — "every rule is an
optimum", the argmax of a stated objective under the MEASURED cost line, never a round number
that felt right.

**§6.1.** Rotating capital, value accrues at `rho(h) = (alpha(h) - c)/h`; setting `rho'(h) = 0`
gives `alpha'(h*) = (alpha(h*) - c)/h* = rho(h*)` — extend the hold until the marginal rate of
edge accrual falls to the average net rate. That is the Faustmann rotation condition from
renewable-resource economics, transplanted intact. For `alpha(h) = a*h^gamma`, `0 < gamma < 1`,
it closes to `h* = [c/(a(1-gamma))]^(1/gamma)`.

I did not test h* against a hardcoded decimal — a formula wrong in the same way twice passes
that. The tests assert the **first-order condition itself** (`rotation_residual == 0`) and the
identities it implies: `alpha(h*) = c/(1-gamma)` independent of `a`, net edge
`= c*gamma/(1-gamma)`, and the doc's corollary that gross edge at `gamma = 1/2` is exactly
`2c`. The **second-order** check is verified numerically rather than taken on trust: a sign
error in the derivation lands on a stationary point that MINIMISES the accrual rate, and every
first-order test still passes.

**§6.2.** `tau* = c` risk-neutral, `c + lambda*sigma` risk-adjusted. A negative `lambda` is
refused: it is the Lagrange multiplier on the vol-target constraint, not a free mood parameter,
and negative means being paid to take variance.

**Turnover is an OUTPUT** and that is enforced by the API surface, not a comment — a test
asserts no `threshold_for_turnover`-shaped function exists for a caller to find. The inversion
("pick the selectivity that hits the turnover we wanted") is the exact reasoning §6.2 refuses.

### The trap the closed form cannot see

`a*h^gamma` grows without bound, so there is ALWAYS an h where gross edge clears any cost line,
and the formula always returns a profitable-looking optimum — including at horizons far past
where `alpha(h)` was ever measured. Real IC-decay curves saturate; a power law fitted to the
first 60 minutes says nothing about 400, and nothing in the returned number says which side of
the data it came from.

So `fitted_horizon` is **required with no default** on the planner, which is the thing that
produces a recommendation, and an optimum beyond it is refused. The primitive stays pure
algebra. The boundary is inclusive — the horizon is the last point the curve WAS measured at —
and that is pinned by a test whose horizon is computed from the cost line rather than guessed,
because `>` and `>=` are invisible on any fixture whose h* does not land exactly on the edge.
`horizon-ge` survived the first run for precisely that reason.

### Two sources disagreed on a boundary and I picked one out loud

§6.2 integrates over `g >= tau`; the Part II family rules say `trade iff |g~| > c + lambda*sigma`.
For a continuous density that is a measure-zero difference nobody notices. The density here is
DISCRETE — the edge grid is a real mapping — so the marginal opportunity lands exactly on tau
and the convention decides whether it trades. Implemented as §6.2 states it, since that is the
section being derived, and pinned by a test so the choice is visible rather than being whatever
the comparison operator happened to be. `turnover-strict-gt` kills.

### Mutations

**26 of 27 across the module**, plus the two boundary cases found and killed. The one survivor
is `best-is-left` — returning the left end of the converged golden-section bracket instead of
its midpoint. They differ by less than the convergence tolerance (relative 3e-9 against a
solver tolerance of 1e-10 of the span), so **no test should distinguish them**: it is an
equivalent mutant, not a gap, and killing it would mean asserting precision the solver does not
claim.

Golden section rather than a root-find on `rho'`: real `alpha(h)` is read off a measured
IC-decay curve, so its derivative is a finite difference of noisy data. The doc states each
subproblem is unimodal on the estimated curves, which is what golden section needs, and it is
deterministic to the last bit on every machine (rule 1). The loop is bounded, not
`while abs(b-a) > tol` — an `alpha` returning NaN makes every comparison false and spins.

## M19 — §6.3, the joint fixed point of tau* and h*

**Red first**: `ImportError: cannot import name 'EdgeCurve' from 'pips.selection.turnover'`.

§6.1 optimises when to exit, §6.2 what to enter, and they INTERACT: `alpha(h)` depends on the
admitted population, so raising the bar changes the edge curve; and the variance a trade carries
depends on how long it is held, so the hold changes the threshold. Solving them separately —
which is what last tick's planner does — answers a different question: each optimal against
inputs the other one moves.

**The failure mode is why this needed care.** Coordinate descent on a map that is not a
contraction does not diverge loudly. It OSCILLATES, and the last iterate is a perfectly
ordinary number, indistinguishable from a converged one. So non-convergence raises, there is no
`allow_unconverged` for a caller to reach for, and a test asserts no such parameter exists. A
cycle is named as a **cycle of period 2**, not as running out of iterations, because the two
call for different actions — "needs more iterations" invites raising `max_iter`, which for a
cycle burns time and returns the same non-answer. The oscillating fixture is not contrived
arithmetic: with `sigma` growing linearly in the hold, tau alternates between 5.3e-4 and 3.2e-2
forever while neither subproblem is wrong.

**The verification is the definition, not remembered decimals.** At the returned pair the
Faustmann residual vanishes on the edge curve of the population admitted at tau*, AND tau* is
the §6.2 threshold for the volatility of a trade held h*. A loop that settled on the wrong point
would pass any test written against stored numbers.

### Relative tolerance, because tau and h are not in the same units

tau is an edge around 5e-4; h is a holding period around 8. One absolute epsilon cannot be right
for both — at 1e-6 it is meaninglessly loose on tau (0.2%) and painfully tight on h. Judged per
coordinate against its own magnitude, and the test for it is unit-invariance: the same problem
in seconds rather than minutes must give the same threshold and a hold scaled by exactly 60.

### On the doc's monotonicity claim — not asserted, and why

§6.3 says "convergence is monotone in the objective". I did not encode that, deliberately. With
`lambda = 0` the joint objective is `N(tau)*(alpha_tau(h) - c)/h` and both steps maximise it —
but then `tau* = c` regardless of h, there is no h→tau coupling at all, and the problem is not
joint. The joint case needs `lambda > 0`, where the monotone quantity is the LAGRANGIAN, whose
risk term depends on a portfolio-volatility model §6.3 does not state. Asserting monotonicity of
the unconstrained objective instead would fire spuriously on every real solve. Inventing a
vol model to make a guard go green would have been the worse choice — so the docstring records
that the claim is not checkable at this level, and the both-conditions check stands in its
place, which is stronger anyway.

### My mutation harness mutated the wrong function

`no-horizon-check` and `horizon-last-only` both reported SURVIVED. Neither had run: the anchor
`if hold > fitted_horizon:` appears **twice** in the file — once in last tick's planner, once in
the joint solver — and `str.replace(old, new, 1)` takes the first, which is the planner. So I
was mutating code the joint-solver tests do not exercise and reading the pass as a survival.

Fourth harness failure in this project and the same family as the other three: **the tooling
silently did something other than what I asked, and the result still looked like a result.**
Fixed by asserting the anchor is UNIQUE before substituting — `assert s.count(anchor) == 1` —
which is what the earlier fixes should have generalised to. Re-run: `no-horizon-check` killed.

### And a real gap behind it

`horizon-first-only` (`step == 0`) then survived legitimately: my fixture put the excursion on
the very first iterate, so it could not tell a check on every iterate from a check on the first
one — while the test's own docstring claimed the opposite. The whole point is the excursion that
happens partway through. New fixture: a thinning curve where a higher bar admits fewer
opportunities, so the fitted scale falls and the optimal hold lengthens — h goes 13.3 → 39.9 →
68.2 against a horizon of 20, starting INSIDE the measured range and walking out. Killed.

§10.2 of the NSE blueprint: the ensemble's internal crossing — one pipeline buying what another
sells — reduces REALIZED turnover below the sum of the parts. The combined-blotter simulation
measures the netting ratio (`1 - external / sum of member turnovers`) and **re-prices the
ensemble's cost line**, which shifts each member's optimal threshold, and S5 iterates that to a
fixed point.

### The netting window is the whole risk

Two pipelines cross only if they trade the same symbol at the same TIME. A buy at 09:20 and a
sell at 14:50 do not cross — both orders reach the market and both pay the cost line. Netting
them on paper books a saving that was never available, which lowers the cost line, which admits
trades that do not clear their real costs, and every number downstream stays plausible. So
`bucket_ns` is **required with no default**: it is the single most consequential parameter here.
A test makes the point by measuring the same two orders at two windows and getting a ratio of
0.0 and 1.0.

Buckets are epoch-aligned, so two orders a second apart can fall either side of a boundary and
fail to net. That UNDERSTATES netting — the conservative direction — and is stated rather than
corrected, because the alternative (sliding windows that chase pairs) reports a saving whenever
one can be constructed.

### The feedback runs the flattering way

Every pass can only lower the cost line, and a lower line can only admit more trades. So the
degenerate answers are refused: a ratio of 1.0 means the ensemble sends nothing to the market,
where its cost per unit of intended turnover is not zero but UNDEFINED — reporting zero would
set τ* to zero and admit every opportunity regardless of edge, and it would look like the best
result the search ever found. Non-convergence raises, cycles are named as cycles, and there is
no `allow_unconverged`.

Units are kept apart deliberately: the cost line is a RATE and is float; blotter turnover is
money and is Decimal. Paise accounting applies to cash amounts, not to rates.

## M19 — order-budget constraints `[C-OBUD-01]`, and M19's last piece

**Red first**: `ModuleNotFoundError: No module named 'pips.selection.order_budget'`.

The blueprint states the purpose exactly: *"order budget respected as an optimizer constraint,
so research never certifies a strategy the engine may not legally run."* The constraint belongs
in SELECTION, not only in the engine — a strategy that clears every statistical gate and then
cannot be run is a strategy that wasted the gates.

Three limits, not interchangeable: **5 orders/second globally** (the governor, deliberately half
SEBI's ~10/s registration-free threshold under the Feb-2025 circular enforced from 2026-04-01),
**2/second per symbol** (three symbols each sitting exactly at their throttle already breach the
global 5), and the broker's **daily cap** — a different dimension entirely, since one order per
second all day never approaches 5/s and still blows past ~3000.

**The governor binds, not the legal threshold.** A strategy at 7 orders/s is legal and still
inadmissible: the governor throttles it, and the throttled strategy is not the one that was
validated. Certifying it certifies a backtest of something the plant will never run.

**Every order event counts, not every fill.** The protected-limit machine (M14) reprices, so one
intent becomes several events. Counting fills understates the rate by whatever the reprice
multiplier happens to be — in the direction that admits the strategy.

### The same question, the opposite answer from netting

The window SLIDES. Fixed one-second buckets hide exactly the bursts this exists to catch: five
orders at 0.9s and five at 1.1s bucket as 5 and 5, both inside the cap, and are ten orders in
200ms. That is the opposite choice from the netting bucket last tick, deliberately — there,
fixed buckets understate crossing, which charges the ensemble for a saving it might have had,
the conservative direction. Here they understate the peak, which hides a violation. **The
same-looking question has different safe answers depending on which way the error flatters.**

### I talked myself into a boundary change and then out of it

The window is half-open, `[t, t+1s)`. I found a case that looked like a missed breach — three
orders at 0.0s, 0.5s and 1.0s against a 2/s throttle reporting admissible — and started
switching to an inclusive window on the "when in doubt over-count" principle.

That was wrong, and the fixture that would have caught it is the one I wrote to justify the
change. Under a closed window, five orders per second SUSTAINED reads as six, because the
boundary order is counted in both neighbouring windows — so every strategy running at exactly
the governor's rate would be refused. Not conservatism; an off-by-one applied systematically.
And nothing is actually hidden by half-open: any burst spanning less than a second sits entirely
inside some window, so the only thing excluded is the boundary instant. Kept half-open, pinned by

written down — the same treatment §6.2's `g >= tau` got.

## M19 — S5 now solves tau* and h* JOINTLY, per §6.3 `[C-TURN-01]`
