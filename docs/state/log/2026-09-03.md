- **A rate-limited stop exits 1.** Exiting 0 tells a scheduler the campaign succeeded, so it

- **Errored keys exit 1** — they were deliberately left unmarked so the next run retries them,

- **A plan that cannot be costed exits 2**, distinct from 1: nothing was attempted, so nothing

## The blocker's cost figure was wrong by 782×, and it omitted the expensive part

With the whole campaign path swept, the honest next question was whether the thing blocking the
project is really blocked. It was not — or not for the reason recorded.

CURRENT.md framed the owner's decision as: daily bars for ~1,800 names cost **~1.4M calls,
~16 quota-days**, so either commit sixteen days or supply a coarser seed. Recomputing it against
the repo's own calendar and config reproduces that number **exactly as the 1-minute row**. The
figure applied the 1m cost model — 1 call per symbol per day, which holds because a 375-candle
session fits one call — to *daily* bars. Three years of daily bars is **782 candles**, inside the
same ≤1,000-per-call cap, so it is **one call per symbol**: **1,800 calls, 0.02 quota-days**.
About 24 minutes of politeness-limited wall clock. Not a spend decision at all.

**But the old framing also never mentioned the input that is expensive.** Daily bars give median
₹volume, Amihud and gap-rate. They cannot give **spread** — OHLC has no spread at any interval —
and `[C-UNIV-01]` requires it: `_usable` drops any symbol missing a component, because *"a
missing spread read as zero makes an illiquid name look tight, which is the flattering
direction"*. The blueprint §4.4 sources spread from **1-second ranges or quote captures** and
scores over the trailing 60 sessions. 1-second is 22,500 candles per symbol-session → 23 calls →
**2.48M calls, 27.6 quota-days** for all 1,800 names. That is the real cost, and it is *worse*
than the number the blocker warned about — for a component the blocker did not name.

The two facts together give the ordering, and it is cheap:

| step | calls | quota-days |
|---|---|---|
| daily bars, ~1,800 names, 3y | 1,800 | 0.02 |
| 1-second, 60 sessions, shortlist of ~600 | 828,000 | 9.2 |
| 1-minute, U300 × 3y (the authorised campaign) | 234,600 | 2.6 |

The cheap seed buys a **shortlist**, and the shortlist is what makes spread affordable. Roughly
**7–9 quota-days end to end**, against a framing that said 16 just to begin.

**So what the owner is actually deciding is the shortlist width, and it is a bias question
rather than a budget one.** Acquiring spread only for the volume-top-N makes the spread z
cross-sectional over N rather than over the eligible list, so a modest-volume name with an
excellent spread can never surface. Spread carries the second-largest weight (−0.75), so N wants
to be comfortably wider than 300. Still the owner's call — but a small one, and a different one.

Flagged rather than buried: `candles_per_call: 1000` is `verified: false` (a blueprint planning
figure — daily survives any plausible cap since 782 < 800, but every 1-second row scales
inversely with it); the `1second` interval's availability and per-symbol history depth are both
still on the M3 probe's outstanding list; and Breeze **omits untraded bars**, so the 1-second
counts are an upper bound that illiquid names will come in well under.

No code changed this tick. The correction is to `docs/state/CURRENT.md` item 1, which is where
the wrong number was doing its damage.

## Correcting the correction: the blocker is a fetch shape, not a quota

The tick above concluded a daily seed costs 1,800 calls rather than 1.4M. That is true of the
**vendor** and false of **this code**, and I should have checked the second before writing the
first.

`budgeted_fetcher` requests `ist_window(day)` — a single IST day — and the manifest and bronze
layout are keyed per symbol-day, which is exactly what makes a resume granular. **So the per-day
toll is paid whatever the interval.** A daily-bar campaign on this fetcher pays 782 calls per
symbol and receives one candle for each of them: the same 15.6 quota-days as 1-minute, not 0.02.

| per 1,800 names, 3y | this fetcher | if one call could span days |
|---|---|---|
| 1day | 15.6 quota-days | **0.02** |
| 30minute | 15.6 | 0.22 |
| 1minute | 15.6 | 5.9 |
| 1second | 359.7 | 351.9 |

The conclusion survives and improves: **the cheap seed is real, and it is gated on a bounded
code change — a range-spanning fetch and a manifest keyed by range rather than by day — not on
sixteen days of quota.** That is engineering work, not an owner decision, which is a better
place for a blocker to sit.

**So the arithmetic now lives in `plan_campaign` instead of in prose.** Twice in two ticks a
seeding cost was written down wrong, both times by applying one interval's model to another, and
both times in a document rather than in code that anyone could run. `CampaignPlan` gained
`interval`, `session_minutes` and `candles_per_call`; `estimated_calls` costs the shape this code
issues, and `estimated_calls_if_ranged` states what the vendor would allow, with `describe()`
printing the gap whenever they differ. The next person to ask what a seed costs runs the planner.

Test-first, six new tests: the per-symbol-day toll at four intervals (1day, 30minute and 1minute
all cost one call; 1second costs 23); the ranged figure beside it; **an unknown interval is
refused rather than costed as a minute** — a typo'd `1min` would otherwise inherit the 1-minute
model and under-state a 1-second plan by 23×; `describe()` names the interval it costed, because
a cost with no interval beside it is a number nobody can check; and `--interval` reaches
`budgeted_fetcher`, which had defaulted to `1minute` with nothing passing it — a plan and a run
disagreeing about what was requested, with the plan the more expensive of the two and therefore
the one that looks conservative.

## Promotion survives a record shape it does not know

The next step on the critical path is the range-spanning fetch that makes a universe seed cheap.
It has a prerequisite, and checking it first turned up a live defect: **a range record kills
`promote_bronze` outright.**

```
RAISED: KeyError 'trade_date'
```

`promote_bronze` assumes every JSON under the bronze root is a 1-minute symbol-day capture. A
range-spanning record — one call covering many sessions — has no single `trade_date`, so the
lookup is a bare `KeyError` out of the loop. That does not skip the record; it **takes the whole
run down and discards every quarantine reason already collected for every other file**. The same
is true of a half-written or hand-edited file: one bad record, a failed run.

A record this function cannot *read* is the fourth quarantine reason, sitting beside the three it
already has — not data, unresolvable identity, no bars survived. It now says which fields
promotion reads and that the record may be a different capture shape or half-written, and the
run continues; the file it *can* read is still promoted.

`request` is required rather than defaulted while I was there. `capture.get("request", {})` still
quarantines — the very next lookup fails — but the reason then names `trade_date` on a record
with no request block at all, sending the reader to look for a date in a structure that was never
there. That distinction is what the last surviving mutant caught.

Contrast worth keeping: the PIT log **refuses to read** on a bad line, and bronze **quarantines
and continues**. Those are opposite answers to the same shape of problem, and both are right. A
PIT row silently dropped changes what an as-of read returns, so a wrong answer is worse than no
answer; a bronze file is independent of its neighbours, and the reason is recoverable from the
record quarantine retains.

`[C-SILVER-01]` records the new reason. `make ci` green: **2069 passed**, ledger 59 rows,

## The capture supervisor: the loop that would run forward capture

`[C-M4-04]` said it plainly one tick ago — the capture writer appears in its own module and its
own test and nowhere else. Of everything open, this is the only item where **delay has a
permanent cost**: history can be backfilled later, and a session that passes uncaptured is
spread and depth that cannot be bought back at any price.

`ws_capture.py` drives the writer from successive connections. Eleven tests, written first
(RED: `ImportError`). Two properties carry it, and they pull against each other:

**A disconnect must leave a mark**, or the archive's gaps are invisible — the failure the GAP
record exists to prevent. **A deliberate stop must not.** A gap recorded at every clean shutdown
— end of session, deploy, an operator stopping the service — fills the archive with outages that
never happened, and a reader who learns to skip gap records has lost the one signal that
matters. So a clean stop is its own exception rather than "the loop ended", and both directions
are pinned by tests that would otherwise each be satisfiable by the wrong implementation.

Mutation found three more, all real:

- **The gap is stamped from the FIRST drop, not the last retry.** Each failed reconnection is
  part of the same hole; re-stamping at every attempt reports the final thirty seconds of a
  two-hour outage — understating it in the direction that makes the archive look healthier than
  it was. Writing the test surfaced a second half I had got wrong: the *reason* was taken from
  the last retry while the timestamp came from the first, so the record described why the outage
  **persisted** rather than what **caused** it — a mixture of two events rather than an account
  of one. Time and reason now travel together.
- **The backoff resets after a successful reconnect**, or a service that drops briefly twice an
  hour ends the day waiting hours between attempts.
- **The feed is closed after a disconnect too**, not only on the clean-stop path. That mutant
  survived because `feed.close()` was called twice on the clean path — explicitly *and* in the
  `finally` — so removing the `finally` was invisible. The dead call is gone; a supervisor that
  reconnects ten times would otherwise leak ten descriptors.

`make ci` caught two of my own slips locally before the push — an unused import and an `object`
that would not compare — which is where they belong.

**Still `building`, and the row says exactly why.** What is missing is the vendor adapter:
Breeze's WS SDK is callback-driven and cannot be exercised without a live socket, so the `Feed`
protocol is the seam and the adapter is the one part that cannot be tested here. Running it is
also a live market-data subscription, which is the owner's to authorise.

## Romano–Wolf: the correction that must not be optional

The multiplicity control — what stops a lucky strategy being called real — and the module where
I shipped and then fixed an α-dependence bug earlier this session, which suggested the area was
thin. 16 mutations, **10 killed, 5 real gaps, 1 equivalent.**

**The stepdown itself was not tested.** `remaining = ordered[position:]` → `[name]` survived:
each hypothesis tested against only itself is not a stepdown at all, but a per-model p-value
with **no family-wise correction**, and every adjusted p comes out smaller — the direction that
manufactures discoveries. Now stated as a comparison between two runs rather than against a
recomputed expectation, so the test cannot be satisfied by the implementation it checks: **adding
a competitor to the family must cost a model significance.**

Getting that fixture right took three attempts, and the failures are the same one twice. A
statistic far beyond every bootstrap draw adjusts to 0.0 whether or not the family is corrected,
so an obvious winner cannot tell a stepdown from its absence — my first fixture reported
`0.0 > 0.0`. My second was periodic, and a block bootstrap reproduces a periodic series and lands
back on the same clean answer. What distinguishes them is a **marginal** edge with **irregular**
noise: a statistic sitting inside the bootstrap distribution rather than beyond it.

**One constant series pins three more.** A zero differential has zero mean and zero variance, so
the statistic is 0 and every recentred draw is 0 — an exact tie at both boundaries at once. The
bootstrap frequency must count draws *at least as extreme*: `>=` gives p = 1.0, and strictly-
greater gives **p = 0.0, turning a model with literally no edge into the most significant result
in the run.** The rejection test is the mirror: `statistic > threshold` leaves it unrejected
where `>=` rejects a zero. And the variance floor is what makes any of it computable — the same
trap `gate_s4` had, where a flat series scored a Sharpe of 4.6e15.

Also: **models of different lengths are refused.** One index set is drawn and applied to every
series, so a longer model would be silently measured over a window the others never saw, making
the family-wise maximum a comparison between different periods.

The equivalent one is the `max_rounds` bound, and its comment already says why it is there: each
round rejects at least one hypothesis or breaks, so it cannot fire — it exists because an
implementation that stopped shrinking `surviving` once looped forever instead of failing. A
safety net for a plausible edit, the `_TERMINAL` species.

`make ci` green: **2110 passed**, ledger 63 rows, determinism bit-identical.

## The plateau ratio, and a median that was one only by accident

`[G-P4-PLATEAU]`'s measurement: median neighbour score over the centre's, against a 0.70 bar.
12 mutations, **11 killed**. The undefined cases hold — an unevaluated centre, a non-positive
one (against zero the ratio is undefined and against a negative it **inverts**, so a worse
neighbour divides to a larger number and reads as a flatter plateau), and fewer than two
evaluated perturbations. So does the property that makes the gate mean anything: **every
evaluated neighbour counts, including the bad ones** — taking the median over only the good ones
would guarantee a ratio above the bar, because the bar is what "good" means. The ratio is not
capped at 1, the mean cannot stand in for the median, and it cannot be inverted.

**The survivor: `sorted()` was load-bearing and nothing tested it.** `around[middle]` is a median
only because the list was sorted first. `_neighbours` enumerates axis by axis — for `(1,1)` that
is `(0,1), (2,1), (1,0), (1,2)` — an order with nothing to do with the scores. Dropping the sort
takes the middle **position** instead of the middle **value**, which is not a median and is not
stable under anything: the same neighbourhood with its axes declared in a different order gives
a different plateau ratio, and the gate compares that number against a fixed 0.70.

The existing fixtures could not tell the two apart because their neighbourhoods were symmetric
or already ordered — the middle position happened to be the middle value. The new one places
them far apart on purpose: sorted it reads 0.60 and clears the bar; in enumeration order it
reads 0.25 and fails a gate the neighbourhood actually passes.

That is the **degenerate-fixture** failure again, and it is now the most common single cause of
a survivor in this sweep: a two-point z-score, a 60-observation `np.std`, a two-symbol budget
loop, a statistic beyond every bootstrap draw, and now a symmetric neighbourhood. Each fixture
was correct and each was too tidy to distinguish the property from its absence.

## M_erank: every error here flatters the result

`multiplicity.py` computes the denominator of the DSR's optimistic bracket, and the direction of

- **Zero trials reported an effective multiplicity of 1.0.** Without the shape guard the
  empty matrix falls through to the single-trial floor and answers *one trial's worth, from

  ordinary case.
- **A 1-D array became an `IndexError` on `.shape[1]`** from inside a multiplicity calculation,

  without the second axis is an ordinary mistake.

`effective_rank` now has its own test file, which it should have had: it is a pure function

inferring from a search that happens to call it.

**The two remaining survivors are not gaps, and they are not the same kind of not-gap.** The
