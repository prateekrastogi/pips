## Mutation sweep, target fifteen: `data/breeze/campaign.py` — the command that spends the money

The driver behind `pips backfill`, and the one piece of that path still unswept. 14 mutations,
**6 survived**, and the reason they all clustered in one place is stark: **`main()` was never
called by any test.** Every existing test exercised `plan_campaign` and `CampaignPlan`, so the
entire CLI — `--dry-run` and every exit code — was unexercised.

**`--dry-run` was not tested to fetch nothing.** That is the whole purpose of the flag: a date
range is two strings and a mis-typed one is a keystroke away, so the plan exists to be costed
before it is spent. A `--dry-run` that reached the fetcher would spend real quota against a
metered daily budget, on the command whose entire point is not to. The test now asserts the
session is never opened and the fetcher never built — and a control test asserts a *real* run
does reach them, so a `main` that fetched nothing at all could not pass both.

**Every exit code was untested, and the exit code is the scheduler's resume signal.**

- **A rate-limited stop exits 1.** Exiting 0 tells a scheduler the campaign succeeded, so it
  stops re-running — leaving a hole no later QC can tell from a quiet market.
- **A budget stop exits 0**, because spending the day's quota is the plan working. A campaign
  costing three days of quota stops twice on the way to finishing, and a scheduler treating each
  stop as failure would page somebody about a backfill behaving exactly as designed.
- **Which means the exit code cannot carry that difference, so the message must.** The last
  mutant survived precisely there: with the budget branch removed the run still exits 0, but
  prints **"campaign complete."** for a run that stopped with work outstanding. Same
  failure-that-looks-like-success this module is built against, aimed at the operator rather
  than the archive. The test now pins the text, not just the code.
- **Errored keys exit 1** — they were deliberately left unmarked so the next run retries them,
  which only helps if something says a next run is needed.
- **A plan that cannot be costed exits 2**, distinct from 1: nothing was attempted, so nothing
  is pending and retrying is pointless. It must also open no session.

Noted, not acted on: `main` reads `config/breeze.yaml` by a **relative** path while the data root
comes from `$PIPS_DATA_ROOT`, so the campaign is cwd-sensitive in one dimension and not the
other. It fails loudly rather than quietly, which is why it is a note.

## The blocker's cost figure was wrong by 782×, and it omitted the expensive part

With the whole campaign path swept, the honest next question was whether the thing blocking the
project is really blocked. It was not — or not for the reason recorded.

CURRENT.md framed the owner's decision as: daily bars for ~1,800 names cost **~1.4M calls,
~16 quota-days**, so either commit sixteen days or supply a coarser seed. Recomputing it against
the repo's own calendar and config reproduces that number **exactly as the 1-minute row**. The
figure applied the 1m cost model — 1 call per symbol per day, which holds because a 375-candle
session fits one call — to *daily* bars. Three years of daily bars is **782 candles**, inside the
same ≤1,000-per-call cap, so it is **one call per symbol**: **1,800 calls, 0.02 quota-days**.
About 24 minutes of politeness-limited wall clock. Not a spend decision at all.

**But the old framing also never mentioned the input that is expensive.** Daily bars give median
₹volume, Amihud and gap-rate. They cannot give **spread** — OHLC has no spread at any interval —
and `[C-UNIV-01]` requires it: `_usable` drops any symbol missing a component, because *"a
missing spread read as zero makes an illiquid name look tight, which is the flattering
direction"*. The blueprint §4.4 sources spread from **1-second ranges or quote captures** and
scores over the trailing 60 sessions. 1-second is 22,500 candles per symbol-session → 23 calls →
**2.48M calls, 27.6 quota-days** for all 1,800 names. That is the real cost, and it is *worse*
than the number the blocker warned about — for a component the blocker did not name.

The two facts together give the ordering, and it is cheap:

| step | calls | quota-days |
|---|---|---|
| daily bars, ~1,800 names, 3y | 1,800 | 0.02 |
| 1-second, 60 sessions, shortlist of ~600 | 828,000 | 9.2 |
| 1-minute, U300 × 3y (the authorised campaign) | 234,600 | 2.6 |

The cheap seed buys a **shortlist**, and the shortlist is what makes spread affordable. Roughly
**7–9 quota-days end to end**, against a framing that said 16 just to begin.

**So what the owner is actually deciding is the shortlist width, and it is a bias question
rather than a budget one.** Acquiring spread only for the volume-top-N makes the spread z
cross-sectional over N rather than over the eligible list, so a modest-volume name with an
excellent spread can never surface. Spread carries the second-largest weight (−0.75), so N wants
to be comfortably wider than 300. Still the owner's call — but a small one, and a different one.

Flagged rather than buried: `candles_per_call: 1000` is `verified: false` (a blueprint planning
figure — daily survives any plausible cap since 782 < 800, but every 1-second row scales
inversely with it); the `1second` interval's availability and per-symbol history depth are both
still on the M3 probe's outstanding list; and Breeze **omits untraded bars**, so the 1-second
counts are an upper bound that illiquid names will come in well under.

No code changed this tick. The correction is to `docs/state/CURRENT.md` item 1, which is where
the wrong number was doing its damage.

## Correcting the correction: the blocker is a fetch shape, not a quota

The tick above concluded a daily seed costs 1,800 calls rather than 1.4M. That is true of the
**vendor** and false of **this code**, and I should have checked the second before writing the
first.

`budgeted_fetcher` requests `ist_window(day)` — a single IST day — and the manifest and bronze
layout are keyed per symbol-day, which is exactly what makes a resume granular. **So the per-day
toll is paid whatever the interval.** A daily-bar campaign on this fetcher pays 782 calls per
symbol and receives one candle for each of them: the same 15.6 quota-days as 1-minute, not 0.02.

| per 1,800 names, 3y | this fetcher | if one call could span days |
|---|---|---|
| 1day | 15.6 quota-days | **0.02** |
| 30minute | 15.6 | 0.22 |
| 1minute | 15.6 | 5.9 |
| 1second | 359.7 | 351.9 |

The conclusion survives and improves: **the cheap seed is real, and it is gated on a bounded
code change — a range-spanning fetch and a manifest keyed by range rather than by day — not on
sixteen days of quota.** That is engineering work, not an owner decision, which is a better
place for a blocker to sit.

**So the arithmetic now lives in `plan_campaign` instead of in prose.** Twice in two ticks a
seeding cost was written down wrong, both times by applying one interval's model to another, and
both times in a document rather than in code that anyone could run. `CampaignPlan` gained
`interval`, `session_minutes` and `candles_per_call`; `estimated_calls` costs the shape this code
issues, and `estimated_calls_if_ranged` states what the vendor would allow, with `describe()`
printing the gap whenever they differ. The next person to ask what a seed costs runs the planner.

Test-first, six new tests: the per-symbol-day toll at four intervals (1day, 30minute and 1minute
all cost one call; 1second costs 23); the ranged figure beside it; **an unknown interval is
refused rather than costed as a minute** — a typo'd `1min` would otherwise inherit the 1-minute
model and under-state a 1-second plan by 23×; `describe()` names the interval it costed, because
a cost with no interval beside it is a number nobody can check; and `--interval` reaches
`budgeted_fetcher`, which had defaulted to `1minute` with nothing passing it — a plan and a run
disagreeing about what was requested, with the plan the more expensive of the two and therefore
the one that looks conservative.

RED before the change: four `TypeError`s, `CampaignPlan` having no `interval` at all.

## Promotion survives a record shape it does not know

The next step on the critical path is the range-spanning fetch that makes a universe seed cheap.
It has a prerequisite, and checking it first turned up a live defect: **a range record kills
`promote_bronze` outright.**

```
RAISED: KeyError 'trade_date'
```

`promote_bronze` assumes every JSON under the bronze root is a 1-minute symbol-day capture. A
range-spanning record — one call covering many sessions — has no single `trade_date`, so the
lookup is a bare `KeyError` out of the loop. That does not skip the record; it **takes the whole
run down and discards every quarantine reason already collected for every other file**. The same
is true of a half-written or hand-edited file: one bad record, a failed run.

A record this function cannot *read* is the fourth quarantine reason, sitting beside the three it
already has — not data, unresolvable identity, no bars survived. It now says which fields
promotion reads and that the record may be a different capture shape or half-written, and the
run continues; the file it *can* read is still promoted.

`request` is required rather than defaulted while I was there. `capture.get("request", {})` still
quarantines — the very next lookup fails — but the reason then names `trade_date` on a record
with no request block at all, sending the reader to look for a date in a structure that was never
there. That distinction is what the last surviving mutant caught.

Contrast worth keeping: the PIT log **refuses to read** on a bad line, and bronze **quarantines
and continues**. Those are opposite answers to the same shape of problem, and both are right. A
PIT row silently dropped changes what an as-of read returns, so a wrong answer is worse than no
answer; a bronze file is independent of its neighbours, and the reason is recoverable from the
record quarantine retains.

`[C-SILVER-01]` records the new reason. `make ci` green: **2069 passed**, ledger 59 rows,
determinism bit-identical.
