## Every ranged daily fetch was silently dropping its first day

Found while sourcing the NSE holiday list, which is the only reason it was findable: yesterday's
data-plane check fetched RELIND for 2026-08-25..29 and got three bars starting on the 26th. I
wrote in the log that the 25th was "almost certainly a holiday, and we cannot tell". **It was not
a holiday** — NSE's own cash-market list, now in hand, has nothing on 2026-08-25.

So I asked three overlapping windows instead of guessing:

```
ask 2026-08-25..2026-08-29 -> ['2026-08-26','2026-08-27','2026-08-28']   25 missing
ask 2026-08-24..2026-08-29 -> ['2026-08-25',...,'2026-08-28']            24 missing
ask 2026-08-21..2026-08-26 -> ['2026-08-24','2026-08-25','2026-08-26']   21 missing
```

The `from_date` day is dropped every time; `to_date` is kept every time.

### The cause is a timestamp convention, not arithmetic

`ist_range` opens the window at **09:15**, the session open. A **daily bar is stamped 00:00:00** —
visible in every archived record — so the first day's bar lies before the window opens and the
vendor excludes it. The end day survives only because the window closes at 15:30, which is after
that day's midnight stamp. Nothing about the code looks wrong; the two conventions simply do not
meet.

`ist_range`'s own docstring called it: *"**The multi-day span itself is UNVERIFIED.** SAL-0002
established the timestamp convention on single-session windows; nobody has asked this vendor for
three years in one call."* It could not have been found by reading. It took asking.

### Fixed, and verified against the live API rather than the tests

`range_open_time(interval)` opens daily windows at 00:00 and leaves intraday at 09:15 — the
latter deliberately, because widening intraday to midnight pulls in PRE-OPEN prints that
`normalize_candles` then clips away, which would be silent damage rather than visible gaps. The
same three windows, re-asked at 00:00:

```
2026-08-25..29 -> 4 bars, 25 present
2026-08-24..29 -> 5 bars, 24 present
2026-08-21..26 -> 4 bars, 21 present
```

Weekends still correctly absent. Sweep 3/3 across both modules, including
`the-fetcher-ignores-the-interval` — a correct helper no caller consults is this project's
signature failure.

### What it costs, which is not nothing

**Every symbol in the 2026-09-04 seed is missing 2023-09-04**, a Monday and not a holiday: 3,101
records, one bar each. Small in volume and systematic in kind, which is the dangerous
combination — a uniform first-day gap does not look like corruption, it looks like the range
starting a day later than it does.

Re-fetching is NOT automatic: the manifest records those range keys as terminal, so a normal
backfill skips them. Recorded for the owner rather than silently re-spent.

`promote_daily` explodes a range record into one row per trading day. Two traps it exists to
avoid, both found by READING the intraday path rather than by hitting them:

* **`normalize_candles` ignores the candle's own date** and stamps every bar with the single

  mutation `every-bar-takes-the-ranges-start-date` is killed by a test that checks the CLOSES
  travel with their days, not merely that the dates are right.
* **the vendor code is resolved PER DAY.** A code can point at different instruments across three
  years; that is the whole reason `resolve_vendor_code` takes a date. The fake master records
  which dates it was asked about, so resolving once is caught.

Everything silver refuses, this refuses the same way and for the same stated reasons: a code that
resolves to no instrument, a reply carrying no data, and a `received_at_ns` of 0 — which is EARLY
rather than absent, sorting inside every as-of window there is.

A day-keyed record is **skipped and counted**, never quarantined: it is not corrupt, it is
silver's. The count is what stops an empty run reading as a clean one — the same lesson `run_qc`

## `gap_rate` defined — BLK-0003 is closed

§4.1 gives the score and defines no component, so `gap_rate` had lived in this repository as a
field name and a `-0.25` weight and nothing else. That made it the one part of the screen that
could not be written without inventing the semantics of what counts as tradeable, which is why it
went to the owner. Approved 2026-09-05:

    move_d   = |open_d / close_{d-1} - 1|
    gap_rate = #{d : move_d > threshold} / #{d : usable}

**A frequency, not a mean magnitude** — one crash day would dominate an average, and "rate" means
how often rather than how far.

**Corporate actions leave BOTH sides.** A 1:2 split is a 50% "gap": counted, the name looks like
the gappiest on the exchange; counted as a non-gap, unusually smooth. Neither is true, so the
pair leaves the sample. It reuses QC's own `jump_explainer` rather than growing a second notion
of an unexplained jump.

**The threshold is config, not a constant** — `config/universe/gap_rate.yaml`, carrying its
source, `threshold_verified: false`, and the fact that it is an owner decision unverified against
any study of NSE overnight moves. Lookback 60 sessions, flagged as a POLICY DIMENSION (§4.1
searches {20,40,60}) rather than something to tune on outcomes.

### Two things the fixtures caught that reading would not have

**Floating point moved the boundary.** `10300 / 10000 - 1` is 0.030000000000000027, so a move of
exactly 3% tested as ABOVE a 3% threshold. Prices are integer paise precisely to avoid this, so
the comparison is cross-multiplied into the same arithmetic: `|open - prev| > t * prev`, in
`Decimal`. The threshold now sits where it is written.

**A mutation showed my exclusion test proved nothing.** With the split as the only move,
excluding it from the denominator gives 0/3 and keeping it gives 0/4 — both zero, so the fixture
passed either way. The replacement puts a real 4% gap beside the split, where the readings
separate: 1/3 against 1/4. Both plausible, one right.

## Pacing on what the API says, not on a number somebody guessed

Owner, asked what this account's real limits are: *"run it to maximum and without any limits,
basis real time responding conditions of api."*

Taken literally, "no limits" would mean hammering the endpoint until it locks the account — the
opposite of running at maximum. Taken as intended: **no FIXED ceiling governs the run**, the
vendor's own replies set the pace, and the limit is discovered rather than declared. That is a
control loop, and the classic shape is additive-increase / multiplicative-decrease.

`AdaptivePacer` speeds up gently on healthy replies and backs off hard, with no ceiling of its
own, the moment one is a rejection. `acquire()` never refuses: there is deliberately no call
counter to exceed, because a preset budget is exactly the guessed number this replaces —
`DailyBudgetExceededError` was raised on one.

Four judgements, each one a mutation in the sweep:

* **RATE_LIMITED is the only signal that slows us.** It is the one reply that means we are
  already over the line.
* **EMPTY is healthy.** A non-trading day legitimately returns nothing; reading it as a pacing
  symptom would throttle a campaign on every holiday.
* **ERROR moves nothing.** It says nothing about our rate — speeding up on it would treat a
  failure as permission, slowing down would throttle the run for an unrelated fault.
* **Backoff has no ceiling; only the floor is fixed.** Whatever the vendor is enforcing, the loop
  must be able to get under it. The floor exists so the loop cannot reach zero delay and spin —
  it is not a rate limit.

The rejection arrives in the BODY (`Status 5`, "Limit exceed") with an HTTP 200, never a 429,
which is why the loop is driven by `ResponseKind` rather than by an exception.

### What it replaces, and why that matters

`config/breeze.yaml` carries 75 calls/min marked in as many words a "CONSERVATIVE PLACEHOLDER",
and 100,000/day on owner confirmation, against SAL-0003's donor measuring 100/min and 5,000/day
on this same vendor. Nothing here has ever settled that 20x disagreement, and it decides whether
the 1-minute campaign takes two days or twenty-four. `observed_rate_per_minute()` and
`describe()` exist so a run REPORTS what it discovered — a campaign that measures the truth and
does not say so leaves those numbers unverified forever.

One of my own tests was wrong and the code was right: it called `observe()` without `acquire()`
and expected `calls` to move. `calls` counts calls actually made, and the real loop is
acquire -> call -> observe. Corrected to that shape.

## Median ₹-volume — the third daily component, and the last one that needed no decision

`BLK-0003` is resolved and `BLK-0004` does not gate the shortlist, so LOOP.md §1.2 says record it
and fall through rather than halt. What CURRENT.md called "arithmetic, not a decision" starts
here.

§4.1 gives `z(log median ₹-volume)` at weight +1.0 and the policy grid says "prefer median/lower
quartile over one-day volume". That is the whole specification: a MEDIAN over the lookback, and
the window belongs to the caller because §4.1 searches it over {20, 40, 60} — the same reason
`amihud_ratio` does no windowing of its own.

### A zero-volume day COUNTS, and that is the opposite of Amihud

The two functions now sit beside each other and treat a dead session in exactly opposite ways,
for reasons that are not symmetric:

* `amihud_ratio` DROPS it. `|r| / 0` is undefined; the day carries no information about that
  ratio, and counting it as a zero contribution would make an illiquid name look tighter.
* `median_rupee_volume` KEEPS it. A session on which nothing traded says a great deal about how
  liquid a name is. Dropping it would let a stock that trades twice a month rank beside one that
  trades every session.

The fixture is built so the readings separate: three sessions, one dead. Counted, the median is
₹1,000; dropped, ₹1,500 — a name that failed to trade for a third of the window would look half
again as liquid as it is.

And the NaN convention inverts with it. A name that never traded is **0.0**, not NaN: zero is the
LEAST liquid reading here, and it is a fact rather than a gap. NaN is reserved for having no
sessions at all, which is a different thing. In Amihud it is the other way round, and that is
written into both docstrings so neither can be read as a slip.

### One choice recorded rather than left implicit

The blueprint names "₹-volume" and does not say WHICH price. Close x volume is used, the standard
proxy; the honest alternative is typical price ((H+L+C)/3) x volume, which is nearer NSE's own
turnover because trades happen through the day rather than at the close. It cannot matter here —
a median over dozens of sessions, logged, then z-scored across a cross-section measured the same
way — but it was a choice and the docstring says so.

A broken bar (close <= 0) is REFUSED rather than contributing ₹0, because ₹0 is indistinguishable
from a legitimate no-trade session and those are different facts.

## BLK-0005: the shortlist needs spread, and spread is what the shortlist buys

Went to write the three-component daily ranking — which I had told the owner, and written into
`CURRENT.md`, was "arithmetic, not a decision". It is neither. Reading `shortlist.py` before
adding a function beside it is what caught it, and the module says so plainly enough that

`build_shortlist` scores with `liquidity_scores`. `_unmeasurable` requires a finite
`relative_spread` and refuses to default it — *"a missing spread read as zero makes an illiquid
name look tight, which is the flattering direction and the one that costs money."* Spread is not
derivable from daily OHLC at any interval; it comes from 1-second capture, which is budgeted for
the 500 names the shortlist selects.

    shortlist needs spread -> spread needs 1-second data -> 1-second data is bought for the shortlist

With no spread anywhere, `build_shortlist` admits nobody. It is not broken. It cannot run yet.

### Two documents in this repository disagree, and both were deliberate

`CURRENT.md`'s ordering breaks the circle with a three-component pre-rank. `shortlist.py` forbids
exactly that, because using M7's own score unchanged is what makes the shortlist *"a superset of
every registered universe by construction — a name cannot enter U300 without already being inside
the 500, which is the entire reason the number is 500 rather than 300."*

That is a real architectural conflict on the critical path, so it is `BLK-0005` and the owner's,
not mine. My read is on the card: Option A, because the 200-name buffer between 500 and 300 is
exactly the slack a ranking difference needs, and the owner's own note on choosing 500 says the
buffer is applied to DATA so a name entering U300 is "already being captured rather than arriving
cold". But the superset property would move from *by construction* to *measured each refresh*,
and the cost is stated on the card rather than glossed: names would be picked for capture by an
ordering missing the term with the second-largest weight.

### Both escape routes are already closed, with evidence

* **Spread for everyone first** is the ~2.5M calls / 27.6 quota-days the shortlist exists to
  avoid.
* **Corwin-Schultz from daily OHLC** is the standard answer and this project rejected it on

  pips carries an AST guard treating any reference to it — even from a test — as a

## Wiring the pacer, and what reading `backfill.py` changed about it

Sequenced the pacer first on purpose: the seed re-fetch is 3,101 real calls, which makes it the
experiment that settles the 75-vs-100/min and 100k-vs-5k/day disagreement `config/breeze.yaml`
has carried unverified since August.

Reading `run_backfill` before wiring changed the design. **It already STOPS on the first
`RATE_LIMITED` reply** — `_decide(kind)` returns STOP because "pushing on would collect more
rejections, and marking this key done would record a hole that looks like a holiday forever."

So the multiplicative decrease barely acts *within* a run: the run is over the moment it fires.
Its value is **across** runs — which it only has if the learned number survives the process. So
the interval is now PERSISTED. Without that, every run restarts at the same optimistic rate and
rediscovers the limit by being rejected, and each rediscovery costs a day's progress.

A corrupt or missing state file falls back to the start rather than failing: a campaign must not
be stopped by its own pacing memory, and a value that cannot be read is not a value that was
learned.
