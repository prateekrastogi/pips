## Tick 4 — M2 chunk: as-of panel view + the permanent leakage canary

One coherent chunk of M2 (LOOP.md §1.5), not the whole milestone: the causality guard and the
tripwire that proves it. Calendars `[C-SESS-01]` and trial identity `[C-ID-01]` remain for
later ticks, and their ledger rows are deliberately NOT flipped.

**`AsOfPanelView`** — the production read path over Polars panels. Three bans are mechanical
rather than advisory, because each is a leak reviewers miss: `day_*` / `*_full_day` (full-day
aggregates, unknowable intraday), `smoothed_*` (`P(S_t | F_T)`, reads the future by
construction), and negative shifts. Banned columns are dropped from `visible()` too, so the
obvious bypass — take the frame instead of calling `column()` — yields a frame that does not
contain them. `join_asof_safe` *refuses* a right frame carrying future rows rather than
filtering it: silently filtering would hide that the caller believed it held information it
cannot have, and that belief is the bug.

**18 adversarial tests**, written first: forward shift, future join, banned-field access via
both paths, the exactly-at-decision boundary, empty visible window, earliest-fill strictly
after the decision.

**The canary — three cheats, one per ban**, kept in the suite forever (§7). Each must be
spectacular unsafely and refused in production. Two controls stop the suite proving nothing:
an honest alpha must SURVIVE the same path (else a guard that refused everything would pass),
and must NOT be spectacular (else the threshold separates nothing).

**RED→GREEN, and one genuine fix (§7.1).**
```
$ uv run pytest tests/unit/core/test_asof_panel.py
E   ImportError: cannot import name 'AsOfPanelView'                       <- RED
$ uv run pytest tests/property/test_leakage_canary.py
E   ModuleNotFoundError: No module named 'pips.alphas.canary'             <- RED
```
Then a second, more useful red: two canaries scored |IC| 0.87, under the 0.90 bar. The test's
own message says *fix the canary, never the threshold*, so the fixture was rebuilt rather
than the bar lowered. Root cause was real: the first fixture used an alternating drift, where
price level and next-bar velocity are ~90 degrees out of phase and correlate to nearly zero.
AR mean reversion (`d_{t+1} = -0.9 d_t`) makes the next move a linear function of the current
deviation, so a feature that knows the day's centre scores perfectly. The smoothed-state
canary was also binary, which ties most ranks and caps achievable IC; made graded.

```
next_bar_return        |IC| = 1.0000
distance_to_day_vwap   |IC| = 1.0000
smoothed_regime        |IC| = 1.0000
honest: lagged volume  |IC| = 0.0071      <- the control, comfortably below 0.90
```
The honest control is lagged VOLUME, not lagged close: on a mean-reverting path the level
genuinely predicts the next move, which is a property of the fixture and not a leak, and
would have failed the control for the wrong reason.

## Tick 5 — M2 chunk: exchange calendar + session states [C-SESS-01] → enforced

**Modelled CAS as a separate venue, not a session state.** §3.15 lists six states including
`CAS` at 15:15–15:35, but the continuous session ends 15:30 — they overlap in wall clock, so
CAS cannot be a phase of the continuous session. It is the closing auction, a different venue,
and the code says so: `in_cas_window()` is independent of `session_at()`, and an instant at
15:20 is simultaneously in the CAS window and `FLATTEN_ONLY` on the continuous tape. Disabled
as an alpha venue per ADR-0004.

**The broker cutoff is a required argument, not a constant.** §3.15 forbids a hard-coded time;
`session_at(ts, broker_cutoff_ns=...)` has no default, so no caller can accidentally get one.
The load-bearing test is `test_the_broker_cutoff_is_data_not_a_constant`: the same instant must
resolve to `LATE_CTS` under a 15:25 cutoff and `FLATTEN_ONLY` under 15:12. If that ever stops
holding, a square-off time has been baked in — which is the failure that breaks silently on the
day a broker moves it.

**Holidays shipped empty, on purpose.** Inventing plausible NSE 2026 dates would be worse than
shipping none: an invented holiday is indistinguishable from a verified one at the point of
use, and would fabricate or delete a trading day in every backtest spanning it. The calendar is
effective-dated data like a fee schedule (rule 6) — it carries `holidays_source` and
`holidays_verified_on`, reports `holidays_verified: false`, and `require_verified_holidays()`
raises. Unverified does not mean unusable: P0–P2 runs on fixtures and needs the session
structure long before the list is sourced at M6.

## Tick 6 — M2 complete: trial identity [C-ID-01] → enforced

**The hash is taken over the model's own dump, not a hand-written tuple**, so a field added to
`TrialIdentity` is hashed by construction. The guard that matters is
`test_every_field_changes_the_trial_id`, parametrised over the model's OWN field list: a field
added later but omitted from the hash fails there. The failure mode it prevents is silent —
two distinct trials that hash alike collide, and the second returns the first one's cached
result, which looks like a successful cache hit rather than a bug.

**A real defect the tests caught.** The first implementation hashed `model_dump(mode="json")`.
Pydantic's JSON serialiser turns a non-finite float into `null` by default, so a parameter of
`inf` and a parameter of `None` produced the SAME trial id — two different trials sharing one
identity and one cached result. `[C-NUM-01]` is explicit that NaN and infinities do not cross
a schema boundary. Fixed by hashing the python-mode dump, where the float survives and
`canonicalize` refuses it. The same strictness now rejects any parameter type the canonical
encoding has no definition for, rather than stringifying it into a collision.

```
$ uv run pytest tests/unit/core/test_trial_identity.py
E   ModuleNotFoundError: No module named 'pips.core.trial'                        <- RED
...
FAILED test_a_non_finite_parameter_is_refused - DID NOT RAISE ValueError          <- RED again,
FAILED test_every_field_changes_the_trial_id[runtime_versions]                       usefully
$ uv run pytest tests/unit/core/test_trial_identity.py -q
.............................                                                     <- GREEN (29)
```
The second red was the valuable one: it surfaced the inf→null collision, which no amount of
reading the code would have shown.

**The cache is not the registry.** `TrialCache` only avoids recomputing an identical trial;
`[C-REG-01]` (M11) is the append-only record of *every viewed trial* (rule 4). A cache hit is
not a reason to skip registering the trial, and the docstring says so, because conflating them
is how "deleted trials" stop being counted. Each entry stores the identity beside the result —
a result without a resolvable identity is not evidence (rule 3).

## Tick 10 — M9 statutory cost stack: all five §3.7 goldens, exact

No human items had landed (main still at `46fbdbd`, no deploy key, no Breeze token), so M4 and

**Rule 13 first.** SAL-0006 (`intraday ac3cba7:src/volarb/costs/nse_fees.py`) is the named
donor. Reading it was worth it and also settled what NOT to take: it is an **options** model —
premium turnover, 0.15% STT on sold premium, F&O exchange rates. Every rate is wrong for cash
equity. What ported is the *structure*: date-aware statutory rates, a per-component `Charges`
breakdown, GST on the service component only, and the discipline of a golden test per rate.
Exactly what salvage.yaml's own note predicted ("port the STRUCTURE and re-verify every
number").

**The rates were DERIVED from the goldens, not recalled.** That distinction matters — writing
down remembered NSE rates would have been fabrication dressed as data. Working backwards:

```
sell - buy = Rs22.00 at Rs1L for BOTH brokers  ->  STT(sell-only) - stamp(buy-only)
                                               ->  0.025% - 0.003% = 25 - 3 = 22        ✓
Flattrade buy Rs6.74 at zero brokerage         ->  (E+IPFT+SEBI) x 1.18 + 3.00 = 6.74
                                               ->  E+IPFT+SEBI = Rs3.17 at Rs1L
                                               ->  0.00297% + 0.0001% + 0.0001% exactly  ✓
```

The set was then cross-checked against four further data points it was not fitted to — the
high-cost line at Rs1L and its RT bps at 50k / 2L / 5L — and reproduces all of them to the
paisa. Those tiers do not share a formula: the brokerage cap (0.03% or Rs20, lower) binds at
50k and not above it, so matching all three is evidence rather than curve-fitting. A separate
test pins that the cap actually binds, so the tier goldens cannot pass by coincidence while
the brokerage rule has silently become a flat fee.

**Rounding is once per order, from the exact sum.** Summing rounded components drifts, and
drifts differently at different notionals — which is precisely how a golden starts failing for
a reason nobody can name.

**A real bug in `ledger-check`, surfaced by being used properly for the first time.** These are
the first `enforced` rows to cite `path::test` node ids rather than bare file paths. The check
scanned `pytest --collect-only -q` stdout for the id as a substring — but under pytest 9 that
output is a per-file COUNT summary. So file-path references had been matching *by accident*,
and a real node id could never match. Fixed by asking pytest to collect the ids and reading
the exit code, which is version-independent, with a per-id fallback so the message names the
offender. It failed loudly rather than passing vacuously, which is the good half of the bug.
