## Tick 2 (continued) — BLK-0001 closed: pips owns its CI controller

**The block's premise was wrong, and the owner said so.** BLK-0001 assumed pips had to use
the controller already on this host, which made a credential the only way forward. It does
not: CI is defined by `casc.yaml`, so pips can own a controller outright and committed config
replaces the credential entirely. Owner's instruction: run without credentials, own tenancy,
separate workspace.

**Built** `ops/jenkins/` — Dockerfile, plugins.txt, entrypoint.sh, casc.yaml, compose,
trigger.sh, README. Pattern ported from `../keeper/deploy/jenkins` (a working controller on
this host); its comments record failures already paid for once, so re-deriving them here
would have cost the same debugging twice. Cited in the README rather than silently copied.
Three pips-specific corrections, each with a silent failure mode:
- **Full clone, not shallow** — `tdd-check` walks history; keeper's own ledger §17.2253 records
  this exact class of failure under a depth-1 checkout.
- **No bind mounts** — the controller drives the HOST daemon through a socket, so
  `-v "$PWD:/app"` resolves against a path existing only inside the controller. The previous
  `Jenkinsfile` had this bug; the workspace is now sent as the docker build context.
- **`^${PIPS_REF}` escaped** — JCasC substitutes before job-dsl sees the file, so a bare
  `${PIPS_REF}` resolved at boot against an empty environment and landed as `<name/>`. The job
  would have built the default branch while showing a parameter that looked functional.
  Caught by reading the generated `config.xml`, not by the build passing.

**CI earned its keep on build #1**, which went red at `COPY ... .python-version`: the file was
in every working tree that had run `uv sync`, and in no clone — `.gitignore` treated it as a
pyenv user preference when it is a project toolchain pin, the same class as the tracked
`rust-toolchain.toml`. A laptop-only green could not have surfaced that. This is precisely
what a merge gate is for.

```
pips-ci #1  m/0-scaffold -> FAILURE   COPY failed: stat .python-version: file does not exist
pips-ci #2  m/0-scaffold -> SUCCESS   all 9 stages; tdd-check OK: 6 commits test-first
```

**Incident: I replaced another project's controller.** The first `make jenkins-up` printed
`Container keeper-jenkins Recreated` inside an otherwise successful build. Compose derives its
project name from the DIRECTORY, and `ops/jenkins` shares that basename with
`keeper/deploy/jenkins` — so both files resolved to project `jenkins`, service `jenkins`, and
bringing pips up adopted keeper's container and overwrote its image. BLK-0001's own danger
note said not to touch that controller. Keeper's data volumes survived (it names them
explicitly) and its controller was restored from its own committed compose, verified back on
:8080 with `forge 1.8.1` and all four jobs. Prevention is a test, not a note:
`tests/unit/test_ci_topology.py` pins an explicit project name, explicit image names,
pips-scoped container/volume names and loopback-only binding.

**RED evidence for the guard (§7.1).** A regression test written after the incident never gets
a natural red run, so the guard was checked against a reconstruction of the pre-fix config:
```

  FAIL  no explicit project name -> compose uses the directory name 'jenkins'
  FAIL  service 'jenkins': no explicit image -> defaults to '<project>-<service>'
  -> 2 failure(s): the guard would have blocked the incident
guard verdict on the CURRENT config: PASS
```
