Writing it surfaced an operational problem I made and then fixed: the research image runs as

## M4 — no image writes the shared volume as root

**Red first**: six failures in `tests/unit/test_container_users.py`, including
`AssertionError: research has no USER`.

Yesterday's silver promotion left a parquet owned by `root` that the VM's own user could not
rewrite. A second promotion would have failed on permissions — **in exactly the case the design
calls safe**, since promotion is idempotent.

The cause was an asymmetry nobody had noticed. `reader.Dockerfile` creates uid 10002 and
`USER pips`; `engine.Dockerfile` creates uid 10001 and does the same; `research.Dockerfile`
declared nothing at all and therefore ran as **root**. Three images write one bind-mounted tree
under three identities, and the two that were careful about it were the two I had not touched.

The uids stay different on purpose — the data plane and the order plane are separate processes
(rule 7), and one identity for all three would make that separation nominal. What they now share
is a **group** (gid 10000), which is what lets one service rewrite another's files without any of
them being root. A test asserts both halves: every image runs as a named user in the shared
group, and no two images share a uid.

`make ci-container` passes with research running as `uid=10003(pips) gid=10000(pips)` — the
risky part, since the venv, the marker file and pytest's caches all live under `/app` and are
created during the build as root. `/app` is chowned for that reason.

**The ownership fix cannot be verified on the laptop.** Docker Desktop rewrites bind-mount
ownership to the host user, so a probe file came back as uid 501 whatever the container's
identity. It is a Linux property and needs arb-vm.

### The deploy rail caught what my local CI could not

The push failed to deploy. The rail's journal:

That is the rail doing exactly what CLAUDE.md claims for it — *"the Jenkins green says it works
from what you actually pushed"* — except the thing that caught it was one layer further out
still, because Jenkins builds research and only the VM builds the other two.

Fixed, and **all three images built and their identities checked** before pushing this time:

```
research  uid=10003(pips) gid=10000(pips)
reader    uid=10002(pips) gid=10000(pips)
engine    uid=10001(pips) gid=10000(pips)
```

Two cheap guards added so this class cannot recur: no Dockerfile line may end in `\\`, and a

### The host tree was never writable by any service

With the images fixed, the VM showed the other half. Every directory under `/srv/pips` was
`drwxr-xr-x`, so the group had read and execute and **no write**:

```
bronze  drwxr-xr-x ubuntu:ubuntu     reader is 10002 — could not create files here
silver  drwxr-xr-x ubuntu:ubuntu     research is 10003 — could not write its own output
pit     drwxr-xr-x root:root         written by the old root research image
```

So the reader could never have written bronze either; those files were put there by something
running host-side as `ubuntu`. **The change surfaced a breakage that predated it** rather than
causing one — the root-owned parquet was the symptom that made it visible.

Fixed with group ownership, group write and setgid on the directories, so any of the three
services can create in a shared directory and new entries inherit the group. `secrets/` is
deliberately excluded and stays `drwx------`: a group-writable credential store is a worse
problem than the one being fixed.

**The proof is the re-promotion**, which is precisely what would have failed before:

```
re-promotion: 2216 bars, 0 quarantined
sha before=fa59543d096f5177 after=fa59543d096f5177  identical=True
-rw-rw-r-- 10003:10000 /srv/pips/silver/bars_1m.parquet
```

Idempotence demonstrated on real data and real permissions, not asserted in a unit test.

before committing that only that line changed and the new value matched the previous one's shape
— a rotation once went in a character short, which is why the shape is worth a glance.

## M20 — the StrategyBundle `[C-BNDL-01]`

**Red first**: `ModuleNotFoundError: No module named 'pips.bundle'`.

The backfill decision is the owner's — external calls, metered budget, their credentials — and
LOOP.md is explicit that a human decision must not halt the project. M19 is complete, so this
falls through to M20, which is entirely internal.

The bundle is what the research factory hands the Rust plant. Three properties carry the weight.

**Every field is covered by the content hash**, computed over the model's OWN fields rather than
a hand-written list — a field added later and forgotten in such a list is exactly what the
coverage test exists to catch, and a list does not grow with the model. The test enumerates the
fields and requires each to change the hash. A bundle that is signed but only partly hashed is
worse than an unsigned one, because the signature invites trust in the parts it does not cover.

**Verification recomputes.** A validator comparing the stored hash to the stored hash validates
nothing, passes every tamper test ever written against it, and looks exactly like one that
works. The realistic tamper is not a forger — it is someone opening the JSON and changing a
number, and an editor does not re-sign. There is a test for exactly that.

**Only registered ops cross the boundary.** §3.9: *arbitrary callables cannot be signed.* That is
"no generative AI in the trading loop" made structural, and the refusal happens at BUILD so an
unsignable bundle never exists to be shipped. `REGISTERED_OPS` is closed, and a test asserts it
holds no escape hatch — an entry like `eval` or `call_python` would satisfy every other check
here while granting precisely what the rule forbids.

### A `match=` that matched the wrong error

`no-content-check` survived: deleting the content-hash comparison entirely still raised, because
the signature check catches a tamper too. My test asserted `match="content"` — and the SIGNATURE
message says *"The content is intact"*. It matched by accident.

The two errors name different causes with different fixes: a file that was edited, versus a key
that does not belong. A verifier reporting one as the other sends the reader to re-derive a hash
that is fine. Tightened to `match="content hash mismatch"`, and a second test holds the other
side. **9 of 9** after.

### On the signature primitive, stated rather than assumed

HMAC-SHA256 from the standard library, which is SYMMETRIC: whoever can verify can also forge.
Adequate while the threat is accident — one operator, one VM, DRY_RUN — and content hashing
carries the real weight. **Not** adequate for a plant running unattended against real money,
where the verifier must be unable to sign. Ed25519 is a stated prerequisite for that, and a
dependency decision this milestone does not need to make; `[C-BNDL-01]` is `building` partly for
that reason, and partly because the Rust boot check, the dossier and the lockbox one-shot run
are still to come.

CI green: **1523 passed**, ledger 36 rows.

## M20 — the certification dossier `[C-DOSS-01]`

**Red first**: `ModuleNotFoundError: No module named 'pips.certification.dossier'`.

The bundle says what will run; the dossier says why anyone believed it should. Blueprint §12.2
fixes eight sections and fixes their content as *all gate values, DSR/PBO/SPA numbers, N at
certification, holdout result*.

**Values, not verdicts.** A dossier recording `dsr_passed: true` has thrown away the only thing
that can be re-checked; one recording `0.97 against a 0.95 floor` can be disputed and falsified.
So `Measurement` has no field to store an outcome in — `passed()` is derived, and a dossier
cannot claim a pass on a failing number because nothing in it says "pass". The test for that is
structural: it enumerates the dataclass fields and requires that none of them is a place to lie.

**Absence must not read as a value.** A completeness check written as `name in section` is true
for `None`, for `""` and for `"N/A"`, and a dossier of placeholders then certifies a strategy
nobody measured — the same shape as a rate-limited HTTP 200, or a NOT_RUN gate read as PASSED.
There is deliberately no way to write "genuinely unavailable": a strategy whose kill thresholds
are unknown is not certifiable-with-a-caveat, it is incomplete. **But zero is a value** — `0.0`
and `False` are results, and `if not value` erases exactly the ones worth arguing about.

**Completeness is not passing.** `complete` asks whether everything was recorded, never whether
it was good. Conflated, a measured failure looks unmeasured and an unmeasured one looks failed —
and the rejection dossier becomes unwritable, which is the artifact rule 4 counts and the one
"top-5 is a maximum, fewer is a valid output" needs.

### The finding: the bundle's signature does not protect the dossier

`StrategyBundle.validation_dossier_hash` covers the dossier's **hash**, not its bytes. Editing
the dossier therefore changes nothing inside the bundle, and `verify_bundle` keeps saying yes —
so anyone who runs the signature check alone can be handed any dossier at all. Only
`bind_dossier` notices, and there is a test that asserts both halves of that in one place:
the bundle verifies, and the binding raises.

The direction is forced and cannot be made symmetric. The dossier is sealed first and the bundle
names it; a dossier naming the bundle back would need a hash that does not exist until the
dossier is sealed. Writing that down matters because the obvious "fix" — put `bundle_id` in the
identity section — is unsatisfiable, and someone would spend an afternoon finding out.

### The schema was wrong and the fixture caught it

The first run failed with `stability carries undeclared field(s) ['pbo']`. §12.2's Stability row
predates the P4 gate list, which adds PBO ≤ 0.25 and SPA p ≤ 0.10 by name — a dossier omitting
them cannot be checked against the gate it was certified under. Added `pbo`, `spa_p` and
`lockbox_result` (the blueprint's "holdout result", named for the artifact that produces it
here), plus `trials_viewed` and `m_erank`: a DSR without the N it was computed at cannot be
re-derived, and understating N *raises* it (§3.6).

### Mutation

18 mutations, **18 killed**. The ones worth naming: `falsy-check` (`value is None` → `not value`,
which makes a zero cost share an absence), `at-most-is-at-least` (turns the worst PBO in the run
into a pass), `complete-includes-failing` (the conflation above), `binding-not-checked`, and
`measurement-tag-dropped` — without the tag a `Measurement` and a plain dict carrying the same
three keys seal to the same hash, so two dossiers with different `failing` reports would bind to
the same bundle.

One mutation reported `ANCHOR NOT UNIQUE (0 occurrences)` — a wrong indent in the spec, not a
survivor. The harness refusing to run it rather than silently matching something else is the fix
from the run where `str.replace(..., 1)` scored two mutations against code the tests never
touched.

CI green: **1563 passed**, ledger 37 rows.

## M20 — the lockbox one-shot run `[C-LBOX-01]`

**Red first**: `ModuleNotFoundError: No module named 'pips.certification.lockbox_run'`.

Two halves already existed and neither of them runs the holdout. M11 records unlocks
(`[C-REG-01]`, append-only, second attempt voids the cycle); M18 refuses the bytes below the
release stage (`SealedLockbox`). The gap between them is where a second look still fits.

**Record before evaluate.** Recording a *successful* unlock is the natural order and it is the
wrong one: an evaluation that crashes has still fetched the sealed window, and a caller who
retries gets a fresh "first" unlock — crash-and-retry reads the holdout as often as it likes
with one row to show for it. The runner cannot know how far the evaluation got before it died,
and the only assumption that cannot silently permit a second look is that it got all the way. So
a crashed run consumes the cycle and the retry is told VOID. Mutation `evaluate-before-unlock`
exists precisely to hold that order.

**A refusal costs nothing.** The mirror: if a stray S3 call burned the cycle's one unlock, any
process could void every certification in flight by asking politely and being told no. So the
seal is checked first, and a refused caller never reaches the ledger.

**The window and the cycle come from the seal.** Asserted structurally, on the signature — the
cheapest way to make the wrong dates impossible is to have nowhere to pass them. A run that
evaluates the training window and reports it as the holdout is what makes the gate theatre.

**An empty result is not a pass**, and it still consumes the unlock, because it looked.

### A fixture whose sentinel was the value under test

`test_an_empty_result_is_not_a_pass[None]` failed at first: the `Evaluation` helper used `None`
as "use the default result", and `None` is one of the empty results the test needed to pass in.
The parametrised case silently ran the happy path. Distinct sentinel object now, with a comment
saying why `None` cannot serve. Same family as the vacuous loops over empty tuples — a test that
runs, passes, and exercises nothing.

### Mutation

12 mutations, 11 killed on the first pass. `whitespace-config-allowed` survived: `config_hash`
of `"   "` was accepted because no test passed whitespace, only `""`. The guard was right and
the test was too narrow — the whitespace version is the one that *looks* filled in, which is the
same absence-in-costume the dossier refuses placeholders for. Parametrised over `"", "   ",
"\t", "\n"`; **12/12** after.

### The ledger comment I had to correct

I cited `[C-DATA-04]` for the `SealedLockbox` from memory. No such row — and checking turned up
that `python/pips/data/lockbox.py` was owned by no row at all. First reading: a silent hole,
since `ledger-check` verifies row → code and never code → row.

Measured it before writing that down, and the measurement contradicted it: **72 of 98 modules
are unowned**. `code:` names one representative module per contract by design — the multiplicity
math under `[C-REG-01]`, the validators under their gates — so rule 4 is a liveness check on a
pointer, not a coverage claim. Making it a coverage claim would turn `code:` into a manifest and
every refactor into a ledger edit. Added `[C-DATA-03]` anyway, because the sealed lockbox is a
distinct enforced contract with its own tests; corrected the comment so it does not leave a
reader believing 71 other modules are equally wrong.

## M20 — certification: top-5 is a maximum `[C-CERT-01]`

**Red first**: `ModuleNotFoundError: No module named 'pips.certification.certify'`.

This is the item M20 actually names, and I had over-scoped the milestone in the last two ticks:
the Rust loader's boot check is §3.9 text but belongs to the Rust plant at P5, not here. M20 is
bundle, dossier, lockbox run, and *top-5 is a maximum — fewer is a valid output*.

**The ceiling only removes.** The dangerous implementation is `sorted(candidates)[:5]`: it
returns five whenever five exist, so the count reports the size of the input while looking like
a finding. Gates first, then the cut. `MAX_CERTIFIED` is a module constant and deliberately not
a parameter — a maximum the caller can raise is a default — and the test for that is structural,
on the signature, the same trick as the lockbox runner having nowhere to pass wrong dates.

**The gates are re-derived, never read.** This is the payoff of `Measurement` having no verdict
field: every pass is recomputed from the value and the threshold it was held to. A gate field
holding a **bare number** is therefore *ungated* — a float carries no threshold, nothing can be
derived from it, and accepting it would let "recorded" read as "passed", which is the stored
verdict wearing a different hat. Nine hard gates, each with its own parametrised rejection test.

**Not placing is not failing.** Sixth place lands in `not_placed`; a PBO failure lands in
`rejected`. Merging them would say the sixth was unsound, which is a much stronger claim than
"there were five better ones".

### The boolean that would have ranked first

`bool-ranks-as-number` survived the first mutation run. `True` is an `int` in Python, so a
boolean landing in `net_return` ranks as a 100% return and sorts to the top — and the dossier
deliberately counts `False` as a *recorded value*, so `check_completeness` will never catch it.
The selector is the only place that can. Guard was already right; the test was missing.
**15/15** after adding it.

### Known gap, stated rather than papered over

The DSR gate reads `economics.dsr` and cannot check that it was computed at N = M rather than
the smaller N = M_erank, which would *raise* it (§3.6). Binding the number to its N needs the
raw Sharpe in the dossier. Recorded on the row; not solved here.

Also corrected: a ledger comment on `[C-LBOX-01]` referred to `[C-DATA-04]`, which does not
exist — see the previous entry.

## M20 — drafting a dossier `[C-WRIT-01]`

**Red first**: `ModuleNotFoundError: No module named 'pips.certification.writer'`.

`[C-DOSS-01]` checks a dossier; this writes one, and the two halves fail in opposite directions.
A checker that is too lax certifies unmeasured strategies. A writer that is too *helpful* does
the same thing one step earlier and leaves no trace: a default of `0.0` for a missing PBO
produces a dossier that is complete, hashes cleanly, binds to its bundle, and is invented.

So the contract is subtractive — fill what can be derived, name everything else in `unsupplied`.
There is no default anywhere in the module; `unsupplied` is where "I do not know" gets said, and
a reader sees it.

**A design hole my own test found.** The first version let the caller supply `net_return` as
evidence. But `[C-CERT-01]` *ranks* on `economics.net_return` — so a caller-supplied value is a
caller-chosen ranking, which is the gate objection one step further along. Both are now derived
from the measured metric and refused as evidence, with different messages: one says a supplied
gate injects a passing `Measurement`, the other says it picks the rank. A reader who hits either
needs to know which.

### Mutation: 12, three survived, all three real

- **`bool-is-usable`** — `float(True)` is `1.0`, a perfect deflated Sharpe from a flag, and it
  converts silently. Second time this session a boolean has slipped through a numeric path.
- **`wrong-direction`** — forcing every gate to `at_least` survived because the direction was
  only ever asserted on `GATE_SOURCES[0]`, which happens to be `at_least`. Both `at_most` gates
  were free to be written inverted. The "asserted on one fixture configuration" failure again;
  parametrised over every gate now.
- **`gate-evidence-allowed`** — deleting the gate branch survived because the derived-path
  branch below it is a superset. Unlike the Pareto guard I deleted for the same reason, this one
  *is* distinguishable and the distinction is worth keeping, so the test now pins each message
  to its own consequence rather than to the path name both contain.

**15/15** after.

### The specification gap this exposes

The writer can draft **three** of the nine hard gates. P4 states a number for DSR (0.95), PBO
(0.25) and SPA (0.10) — and only `dsr_min` also appears in `gates.yaml`. Plateau stability,
concentration and the four cost/delay stress gates are named in P4 **without a bar anywhere**:
not in prose, not in the gates ledger, not in code. So no drafted dossier can pass
`[C-CERT-01]` until those six thresholds are decided and recorded, and inventing them to make
the pipeline run would be exactly the failure this module exists to refuse.

A test pins the list of six, so closing the gap has to touch a test that says it existed. This
is now the top next action: it is a decision, not a coding task.

## M20 — the bundle writer `[C-WRIT-02]`

**Red first**: `ModuleNotFoundError: No module named 'pips.certification.bundle_writer'`.

`[C-WRIT-01]` may return a *partial* dossier, because there the gap is the finding. A bundle has
no partial form: `build_bundle` signs it, and a signed artifact carrying an invented `code_hash`
is worse than an unsigned one — the signature is precisely what invites the plant to trust it.
So this refuses, naming everything it lacks in one message rather than one per rebuild.

The dossier hash is derived, never supplied (a caller who can pass it binds a bundle to evidence
that does not exist). An incomplete dossier cannot be signed. A hash that is not a lowercase
64-hex digest is refused — `[C-REG-01]`'s argument about snapshot roots, applied to the artifact
the plant executes. An empty or inverted validity window is refused: it is a bundle that is never
valid while looking bounded.

`REQUIRED_PROVENANCE` is enumerated from `StrategyBundle`'s own fields, and `is_hollow` is
imported from `[C-DOSS-01]` rather than re-implemented — two definitions of "this says nothing"
would drift, and the bundle is the worse place to hold the looser one. (That meant promoting
`_is_hollow` to public, which is the honest way to share it.)

accepted into the dossier: Measurement(value=0.99, threshold=999.0, direction='at_most')

## M20 — driving a certification cycle `[C-RUN-01]`

**Red first**: `ModuleNotFoundError: No module named 'pips.certification.run'`.

Every piece existed. What did not was the **order**, and the order is the whole design.

**The holdout confirms; it never selects.** Finalists are chosen on development evidence alone,
and only then is the lockbox opened — once, for all of them together. A candidate that was not a
finalist is never certified, however well the holdout would have treated it: promoting one after
the fact is selection on the holdout, and reaching for a second look to check would void the
cycle (§3.6).

**An empty field never opens the box.** Nothing to confirm, and an unlock recorded against no
result is a look nobody can account for. **Signing follows the holdout**, so the signature covers
the holdout result rather than a promise of it.

Split `certify.gate_reasons` out of the completeness check so the pre-holdout screen and
certification share one definition of "the gates pass". Two would drift, and the one deciding
who gets the single look is the worse to lose.

### The test that was weaker than the code

`test_a_non_finalist_is_never_certified…` failed at first — because the code refused the run
outright. My holdout stub returned a result for the rejected candidate, and the stowaway check
caught it. The property is enforced **more strongly** than I had written the test to expect:
a non-finalist cannot even be *measured*, let alone certified. Rewrote the stub so it would rate
the rejected candidate 99.0 *if asked*, and asserted it never is.

### A defect the fixture found

My `provenance_for` helper set `strategy_id` to `f"{sid}-strategy_id"`, and the assertion failed
with `['GOOD-strategy_id'] != ['GOOD']`. Sloppy fixture, real hole: **`Nominee.strategy_id` and
`bundle.strategy_id` are two names for one thing and nothing tied them.** Disagreeing means the
run reports finalists under one id and certifies under another, which no audit can reconcile.
Now refused — not overwritten, because silently correcting it hides a bundle built from the
wrong config.

### Mutation: 14, two survived, both my tests being incomplete

- **`rank-ascending`** — `sort(reverse=True)` survived because the cap test asserted only *how
  many* finalists there were, never *which*. The single holdout look would have been spent on
  the five **worst** candidates and nothing would have said so.
- **`out-ranked-silently-dropped`** — the three that miss the cut vanished from `not_finalists`
  unnoticed, reporting a field of five where eight were considered.

**14/14** after asserting the identities rather than the counts. Also killed `gaps-precedence-bug`
(`set(a) | set(b) - {x}` binds as `set(a) | (set(b) - {x})`) — I wrote the parentheses
deliberately after hitting that exact precedence trap in a test earlier this session.

### The honest end-to-end state, pinned

`test_a_dossier_from_the_writer_cannot_reach_the_holdout_yet` runs a real drafted dossier through
the whole pipeline and asserts: nothing certified, the box never opened, and the report naming
`stability.concentration`. That is a finding, not a failure — and inventing the bar to turn it
green is the one thing `[C-WRIT-01]` exists to refuse.

## M20 — carrying what the registry already knew `[C-SMOKE-01]`

**Red first**: `ImportError: cannot import name 'evidence_from_registry'`.

`certify-smoke` reported 38 fields the factory "cannot supply". Five of them the **registry was
already holding**: family, universe policy, session mask, capital tier, broker — all written by
the search into every `RunRecord`, and `Candidate.id` is the `run_id`, so they were one lookup
away. That is `[C-NOM-01]`'s argument a layer down: a value the search recorded must not be
re-typed, because re-typing is how a dossier comes to describe a slightly different run.

Parents too: a promotion is a **new row for the same config at a higher stage**, so the parents
are the earlier rows carrying that config hash. Not a guess and not the whole registry.

**38 → 34.**

### An empty tuple would have lied

`identity.parent_experiment_ids` as `()` is **hollow** by the dossier's own rule, so a run with
no ancestors would have reported "this run has no parents" as "nobody recorded the parents" —
the exact conflation the subsystem exists to refuse, arrived at by accident. The value is always
a string now: the ids, or an explicit `none: no earlier runs recorded for this config`.

### Two fields were in both sources

`broker` and `capital_range` came from the run report *and* the registry row. A field supplied
twice means a merge silently prefers one. They are not interchangeable — the run report is
per-**run**, the registry row per-**candidate**, and the per-candidate answer is the truthful one
the moment a search spans more than one venue or tier. Per-candidate wins, and a test now
asserts the two sources are disjoint.

### A guard no test could distinguish

`parents-include-self` survived: `other_id != run_id` is redundant because the **strict** rank
comparison already excludes self — a row cannot outrank itself. Same call as the Pareto guard
earlier in the project: a claim nobody can check is not a safeguard. Removed, and the strictness
is pinned instead by a test that a same-stage sibling is not a parent — which is the property
that actually matters, since `<` becoming `<=` would make every run its own ancestor.

`session-and-universe-swapped` and `empty-lineage-left-hollow`.

`stability.concentration` and on metrics no validator feeds into S5 yet), the **stress battery**

## M18 — the S4 deflated-Sharpe gate `[G-S4-DSR]`

**Red first**: `ModuleNotFoundError: No module named 'pips.search.funnel'`.

Before idling on the owner's two decisions I listed every `planned` ledger row. Eight sit in M21
and M23 (Rust plant, order plane — later phases). **One sat at M18**, an *earlier* milestone than
the active one: `G-S4-DSR`, `code: null`, `enforced_by` pointing at a `funnel.py::gate_s4` that
did not exist. It is also why `certify-smoke` lists `economics.dsr` as unsuppliable — nothing
computes a DSR anywhere in the search.

**The verdict reads N = M, never N = M_erank.** Understating the trial count *raises* the DSR,
and `M_erank ≤ M` always, so deflating by the effective count is the flattering direction. Both
ends are computed and reported — §3.6 asks for the bracket — and only the conservative one
decides.

That property is easy to assert vacuously, so it is pinned by a fixture where the two ends
genuinely straddle the bar: candidate 3 scores **0.874 at N = M and 0.958 at N = M_erank**. A
gate reading the effective end would admit it. I found those means by probing rather than
guessing — my first fixture had Sharpes so strong that everything passed at both ends, and the
test asserted nothing. It failed loudly, which is why the assertion carries its own "this
fixture proves nothing" message.

**N is every trial ever viewed.** On the smoke registry that is 403 trials against an effective
rank of **2.99** — because only three runs preserved returns. A gate deflating by "how many am I
looking at right now" would use 3.

## M18/M20 — wiring the DSR into the search, and the first gate that rejects on a number

**Red first**: four failures in `tests/unit/test_s5_registry.py`, headed by
`test_derived_metrics_reach_the_candidate` — `run_s5_from_registry() got an unexpected keyword
argument 'extra_metrics'`.

`gate_s4` existed but nothing called it, so `economics.dsr` was still absent from every dossier.

**The DSR cannot live in the registry row.** It is deflated against *every* trial in the ledger,
and the row was written before the trials that deflate it existed. So it joins at **selection
time**: `run_family_searches` runs the gate after every promotion — including the promotion rows
themselves, since deflating against a smaller N raises the DSR — and passes the bracket into S5
as a derived metric.

`extra_metrics` **may not overwrite a recorded metric.** The runs table is append-only precisely
so a ranking cannot be changed after the fact, and a keyword argument that silently replaced
`net_return` would undo that from the caller's side. A run named in the mapping that is not among
the candidates is refused rather than ignored: a mapping that has drifted from the population is
one nobody has checked, so the rest of it is not applied either.

## M20 — the plateau MEASUREMENT, as distinct from the plateau selection `[G-P4-PLATEAU]`

**Red first**: `ImportError: cannot import name 'plateau_ratio' from 'pips.validation.plateau'`.

`G-P4-PLATEAU` says *median perturbed net SR ≥ 0.70 × centre*. On an evaluated grid, one step
along an axis **is** the ±20–30% perturbation, so the ratio is the median axis-neighbour score
over the centre's.

**Every evaluated neighbour counts, including the bad ones.** Taking the median over only the
*good* neighbours would guarantee a ratio above the bar — because the bar is what "good" means —
and the perturbations that went badly are exactly the evidence the gate is asking for.

a score nobody measured), a **non-positive** centre (against a negative one the ratio *inverts*,
so a worse neighbour divides to a larger number and reads as a flatter plateau), or fewer than
two perturbations. And not capped at 1 — a neighbourhood better than its centre says the centre
was not the peak, which is a real observation to keep.

It is not. That ₹3.00 is stamp duty at a ₹1 lakh notional — `0.003% × 1e5` — so it is
proportional. **Every component in the schedule is proportional**, and the only non-proportional
term is the brokerage *cap*, which is a ceiling rather than a floor. Flattrade charges zero
brokerage at all.

So the cost is a constant fraction of notional at every size, and **a minimum economic ticket
does not arise from costs at all.** It arises from **integer shares**: you cannot buy 0.4 of a
₹3,000 stock, so the smallest ticket is one share at its price — which needs a price, which needs
the panel. With proportional costs the question "below what size is this uneconomic?" has no
answer; the honest form is "does edge exceed cost", which is size-independent and is already
`economics.breakeven_edge`.
