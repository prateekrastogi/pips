### The vendor code is not the symbol

Bronze is keyed by `RELIND`; the exchange calls it `RELIANCE`. Only **172 of 5,851** instruments
have the two equal, so writing bars under the vendor code would mislabel almost every name — and
the bars would look perfectly ordinary while joining to no universe, cost model or corporate
action. An unresolvable code is quarantined rather than passed through.

ADR-0001 had already settled the other identity question empirically: Breeze is OPEN-labelled and
ingest adds one interval, probed by a price identity rather than by counting candles. A 09:15
candle covers `[09:15, 09:16)`, so it is the bar ending at 09:16. Off by one interval is a
one-bar lookahead, which backtests love.

### The container writes as root

Writing it surfaced an operational problem I made and then fixed: the research image runs as
root, so `/srv/pips/silver/bars_1m.parquet` came out owned by `root` and the VM's `ubuntu` user
could not rewrite it. **A second promotion would have failed on permissions** — and promotion is
supposed to be idempotent, so it would have failed in exactly the situation the design promises
is safe. Chowned to `ubuntu`.

The general case is unfixed: anything the container writes to a bind-mounted host path is
root-owned. The fix is a `user:` on the compose service, which touches trading-path services and
is not a thing to change in passing at the end of a tick.

## M4 — no image writes the shared volume as root

**Red first**: six failures in `tests/unit/test_container_users.py`, including
`AssertionError: research has no USER`.

Yesterday's silver promotion left a parquet owned by `root` that the VM's own user could not
rewrite. A second promotion would have failed on permissions — **in exactly the case the design
calls safe**, since promotion is idempotent.

The cause was an asymmetry nobody had noticed. `reader.Dockerfile` creates uid 10002 and
`USER pips`; `engine.Dockerfile` creates uid 10001 and does the same; `research.Dockerfile`
declared nothing at all and therefore ran as **root**. Three images write one bind-mounted tree
under three identities, and the two that were careful about it were the two I had not touched.

The uids stay different on purpose — the data plane and the order plane are separate processes
(rule 7), and one identity for all three would make that separation nominal. What they now share
is a **group** (gid 10000), which is what lets one service rewrite another's files without any of
them being root. A test asserts both halves: every image runs as a named user in the shared
group, and no two images share a uid.

`make ci-container` passes with research running as `uid=10003(pips) gid=10000(pips)` — the
risky part, since the venv, the marker file and pytest's caches all live under `/app` and are
created during the build as root. `/app` is chowned for that reason.

**The ownership fix cannot be verified on the laptop.** Docker Desktop rewrites bind-mount
ownership to the host user, so a probe file came back as uid 501 whatever the container's
identity. It is a Linux property and needs arb-vm.

### The deploy rail caught what my local CI could not

The push failed to deploy. The rail's journal:

```
reader.Dockerfile:19
  18 |     && groupadd --system --gid 10000 pips \\
  19 | >>>     && useradd --system --create-home --uid 10002 --gid 10000 pips
failed to solve: dockerfile parse error on line 19: unknown instruction: &&
ALERT: up -d failed for breeze-reader
giving up on 4e92be580d70 after 3 attempts — human needed; not retrying
```

I wrote a **literal `\\`** into reader and engine. A line ending in `\\` is an escaped
backslash, not a continuation, so Docker read `&& groupadd … pips \\` as a completed instruction
and the next line's `&&` as a new one. The edit went through two different quoting paths in the
same script and research got a correct single `\`.

**`make ci-container` passed, because it builds RESEARCH — the one file that was right.** I
changed three Dockerfiles and built one. The other two are built only by the deploy rail, so
nothing local could have failed.

Nothing broke in production: the rail refused to promote a build that would not build, retried
three times, stopped and said "human needed", and `breeze-reader` stayed on the last good image.
That is the rail doing exactly what CLAUDE.md claims for it — *"the Jenkins green says it works
from what you actually pushed"* — except the thing that caught it was one layer further out
still, because Jenkins builds research and only the VM builds the other two.

Fixed, and **all three images built and their identities checked** before pushing this time:

```
research  uid=10003(pips) gid=10000(pips)
reader    uid=10002(pips) gid=10000(pips)
engine    uid=10001(pips) gid=10000(pips)
```

Two cheap guards added so this class cannot recur: no Dockerfile line may end in `\\`, and a
line ending in a single `\` must be followed by a continuing line. Reintroducing the bug fails
the first one.
