## `config/gates.yaml` cannot claim a gate that nothing enforces

Found mechanically, not by reading prose: a scan for config keys that appear nowhere in

### RED

```
FAILED test_a_threshold_enforced_by_nothing_says_so_and_means_it
FAILED test_the_four_unenforced_thresholds_are_named
```

### The finding

`config/gates.yaml` called itself *"numeric thresholds the funnel enforces"* and claimed
*"every value here has a matching row in docs/ledger/gates.yaml"*. Both were checkable. Four
values had no ledger row and appeared nowhere in the code:

- `s4_certification.min_test_trades: 400`
- `s4_certification.pairwise_pnl_corr_max: 0.5`
- `p3_gate.net_sharpe_min_zero_cost_line: 1.5`
- `p3_gate.net_sharpe_min_high_cost_line: 1.0`

I checked each against the plausible alternative before calling it: the `400`s in the code are
S1's halving budget in **bars**, not a trade count; `cluster.py`'s correlation threshold is a
caller-supplied parameter on `1 - corr` distance, a different number reached a different way;
there is no net-Sharpe floor anywhere. They are populated numbers that read as live bars and
are enforced by nothing.

**The code is not at risk.** The funnel's bars are bound to `docs/ledger/gates.yaml` by the
ledger-agreement test, so a wrong constant fails. The hazard is the second declaration: this is
the file a person reads, and a number here drifting from the enforced one has nothing to say so.

### The principle the file already half-stated

> Populated as each gate's milestone lands; **empty values are not defaults, they are gaps.**

Right, and incomplete. The inverse is the more dangerous half, because an empty threshold is
obviously missing while a filled one that nothing consults looks exactly like a gate that
passed: **a populated value is not a gate unless something reads it.** That is now in the header
and checked by `enforced_by`, which maps every threshold to the `G-*` row that carries its live
value, to a contracts row, or to `null`.

### The test caught my own first mapping

I mapped `stress.cost_multipliers` → `G-P4-COST15`, which sounds right and is wrong in kind:
that row's `value` is a net-return **floor of 0.0** at one point of the grid ("still positive at
1.5x cost"), and the grid here is the input those points are drawn from. The equality test
failed with `[1.0, 1.5, 2.0] == 0.0` and I corrected both grids to `null`.

Worth recording because it is the first time this session a test I had just written caught *me*
rather than the code — which is the only evidence that the check is doing work.

### Both directions, and an escape hatch that is itself checked

`null` has to stay true or it rots the other way: a bar wired up later while this still says
`null` understates the system, and the next reader — told it is not live — will not look. So
each `null` is checked against the source, and no key it names may appear in `python/`.

That immediately hit a real collision: `delay_bars` exists in `s1.py` as an unrelated function
parameter for the +1-bar stress run. So there is an `unread_name_collisions` map — and a test
that every entry in it is a **real** collision, because "trust me, it is unrelated" is exactly
what this file is trying to stop.

## The trial cache could poison itself

Followed the thread I named last tick: the project's own warnings are where the remaining
defects of this kind live. `core/atomic.py` says *"two copies of a rule are two places for it to
drift"* — so the question is whether every durable write actually goes through it.

Most direct `write_text` calls are safe by construction: bronze records and quarantine entries
write a **new, uniquely-named** file each time, so a crash leaves a partial new file rather than
destroying a good one, and promotion already quarantines what it cannot read. Fixtures are
regenerable.

`TrialCache` was neither.

### The finding

`put` wrote with `path.write_text`; `entry_for` read with a bare `json.loads`. A kill mid-write
leaves a truncated entry, and **every subsequent lookup of that trial id raises — permanently**,
until someone deletes the file by hand. It surfaces as the search crashing on a trial it has run
before, long after the crash that caused it.

### Which answer applies was decided by the class, not by me

This codebase has a settled response to half-written state, and it is not "raise":

> `Manifest.load` — *"Starting from empty re-fetches, which costs budget; assuming everything is
> done would leave silent holes. Cost is the better failure."*

But that rule is not universal, and applying it blindly would have been wrong. `TrialCache`'s own
docstring draws the line: *"Deliberately not the experiment registry `[C-REG-01]`: the registry
is the append-only record of every viewed trial (rule 4), while this only avoids recomputing an
identical one."* A cache that cannot read an entry has missed, and a miss costs a recompute.
Silently missing would be the **wrong** answer for the registry, where an uncounted trial
flatters deflation — which is exactly why the distinction was worth reading.

Both halves fixed: atomic write so a truncated entry is not produced, tolerant read so one
already on disk costs a recompute and self-heals on the next store.

### Two of my own mistakes, both the same shape

**My `TrialIdentity` fixture invented eleven field names**; pydantic rejected nineteen. The real
set was sitting in `tests/unit/core/test_trial_identity.py`.

**The sweep caught a survivor.** I tested the non-object case with `"null"` — the one value that
gives the right answer *without* the guard, because `json.loads("null")` is already `None`. Now
parametrised over `3`, `[]`, `"a string"` and `null`, with that reason recorded in the test so
the next reader knows why the list is not just `null`.

Sweep 4/4 after the fix.

Sweep 6/6, from 3/5 on the first pass — the two survivors were a missing `-h` case and that

## The control caught my own vacuous test

Went to answer the question I had flagged twice and never checked: are the seed's 411 zero-bar
symbols delisted names, or a data hole? Classified them against the instrument master at both
edges of the window.

I added a control — the same test over the 2,690 symbols that DID return bars — on the theory
that if "present all window" is a meaningful bucket, the fetched names should land in it
overwhelmingly. Result:

```
master live at start: 5851 | at end: 5851
    411  PRESENT all window, yet returned no bars
control: of 2690 symbols WITH bars, 2690 are live in the master at window end
```

Both edges return the entire master. Every symbol is "present all window", so the bucket
distinguishes nothing. Without the control I would have written *"all 411 are listed the whole
window, therefore this is a data hole"* — false, and alarming.

### Why `as_of` is a constant function

```
rows: 5851
valid_from: {'1990-01-01': 5851}
valid_to  : {None: 5851}
```

Every instrument is live from 1990 to forever. **The master has no listing history.**

### Which matters far beyond the 411

1. Nothing can compute `EligibilityInputs.sessions_listed`; it is `None`.
2. `eligible_on` records it as **undetermined** — *"the warm-up cannot be checked"* — rather
   than guessing.
3. `eligible = not ineligible and not undetermined`.
4. `snapshot.py` excludes it.

**Every one of the 5,851 instruments would be excluded and the universe would come out empty.**
Every step of that is the code being right and refusing to invent; the gap is in the data.

The fix is not another master download: `sessions_listed` is *derivable from the daily bars* —
the count of sessions a symbol has one — which the seed already holds. So the daily bars feed
eligibility as well as the ranking, and BLK-0003 now records that as a third consumer.

And the 411 answer falls out: their `sessions_listed` is **0**, so they are ineligible under any
warm-up (60/120/250). Not a hole — the screen working. PANSTE's 8 bars, the same.
