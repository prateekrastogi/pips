## `config/gates.yaml` cannot claim a gate that nothing enforces

Found mechanically, not by reading prose: a scan for config keys that appear nowhere in
`python/` as an identifier. Yesterday's `candles_per_call` finding was one instance of that
shape, so the question was whether it was the only one.

It was not, and the second one is on the certification bars.

### RED

```
FAILED test_every_threshold_says_what_enforces_it
FAILED test_a_threshold_bound_to_a_ledger_row_equals_it
FAILED test_a_threshold_enforced_by_nothing_says_so_and_means_it
FAILED test_the_four_unenforced_thresholds_are_named
```

### The finding

`config/gates.yaml` called itself *"numeric thresholds the funnel enforces"* and claimed
*"every value here has a matching row in docs/ledger/gates.yaml"*. Both were checkable. Four
values had no ledger row and appeared nowhere in the code:

- `s4_certification.min_test_trades: 400`
- `s4_certification.pairwise_pnl_corr_max: 0.5`
- `p3_gate.net_sharpe_min_zero_cost_line: 1.5`
- `p3_gate.net_sharpe_min_high_cost_line: 1.0`

I checked each against the plausible alternative before calling it: the `400`s in the code are
S1's halving budget in **bars**, not a trade count; `cluster.py`'s correlation threshold is a
caller-supplied parameter on `1 - corr` distance, a different number reached a different way;
there is no net-Sharpe floor anywhere. They are populated numbers that read as live bars and
are enforced by nothing.

**The code is not at risk.** The funnel's bars are bound to `docs/ledger/gates.yaml` by the
ledger-agreement test, so a wrong constant fails. The hazard is the second declaration: this is
the file a person reads, and a number here drifting from the enforced one has nothing to say so.

### The principle the file already half-stated

> Populated as each gate's milestone lands; **empty values are not defaults, they are gaps.**

Right, and incomplete. The inverse is the more dangerous half, because an empty threshold is
obviously missing while a filled one that nothing consults looks exactly like a gate that
passed: **a populated value is not a gate unless something reads it.** That is now in the header
and checked by `enforced_by`, which maps every threshold to the `G-*` row that carries its live
value, to a contracts row, or to `null`.

### The test caught my own first mapping

I mapped `stress.cost_multipliers` → `G-P4-COST15`, which sounds right and is wrong in kind:
that row's `value` is a net-return **floor of 0.0** at one point of the grid ("still positive at
1.5x cost"), and the grid here is the input those points are drawn from. The equality test
failed with `[1.0, 1.5, 2.0] == 0.0` and I corrected both grids to `null`.

Worth recording because it is the first time this session a test I had just written caught *me*
rather than the code — which is the only evidence that the check is doing work.

### Both directions, and an escape hatch that is itself checked

`null` has to stay true or it rots the other way: a bar wired up later while this still says
`null` understates the system, and the next reader — told it is not live — will not look. So
each `null` is checked against the source, and no key it names may appear in `python/`.

That immediately hit a real collision: `delay_bars` exists in `s1.py` as an unrelated function
parameter for the +1-bar stress run. So there is an `unread_name_collisions` map — and a test
that every entry in it is a **real** collision, because "trust me, it is unrelated" is exactly
what this file is trying to stop.

## A trial's broker and tier, joined back to what was pre-registered

Continuing the mechanical scan that found the last two units. Alongside `config/gates.yaml`, it
flagged three fields declared in every alpha spec and read nowhere: `target.price_convention`,
`cost_context.must_clear`, `cost_context.capital_tiers`.

**Two of those are non-findings.** `price_convention: "close-to-close on close-labelled bars"`
and `must_clear: "net of the §3.7 statutory line and the high-cost reference line"` are prose.
A test cannot hold a sentence, and they are design documentation in a pre-registration file, not
thresholds claiming to be enforced. Unlike `gates.yaml`, they do not read as live bars.

The third was real, and pulled a second one with it.

### The finding

`TrialContext` carries `broker` and `capital_tier` into every row of the trial registry, and
rule 4 makes that registry load-bearing: every viewed trial counts, and the count only means
something if the rows join back to what was pre-registered. Both were bare literals, diverging
from the specs in two different ways:

- **S1 records `broker="NONE"`**, which no spec declares — every alpha spec says
  `brokers: ["FLATTRADE"]`.
- **Both stages record `capital_tier="2L"`** while every spec declares
  `capital_tiers: ["2L", "5L", "10L"]`. The evidence covers one of three declared tiers, with
  nothing saying so.

The first is almost certainly deliberate — S1 screens before any cost model is applied, its
`cost_model` is 64 zeros, so no broker's schedule has touched the numbers and naming one would
be a claim the run cannot support. **The problem is that nothing said it was deliberate.** A
bare `"NONE"` in a registry column is exactly what a mistyped broker id looks like: both join to
nothing, and the ledger cannot tell them apart.

### RED

```
E   ImportError: cannot import name 'NO_BROKER' from 'pips.search.trials'
```

### What changed

`NO_BROKER` is named once, with a docstring saying what it means and why S1 uses it, and a test
holds it **distinct from every declared broker** — if `"NONE"` ever became a real broker id, the
sentinel and the value would be indistinguishable and the test says so.

`CAPITAL_TIER` gains a docstring recording the coverage gap at the constant: one of three
declared tiers, and `must_clear` cannot be answered for the other two from evidence gathered at
this one. The test holds the recorded value inside the declared set — which catches a typo and
**cannot manufacture the missing runs**, and says so rather than implying the gap is closed.

`BROKER` is bound to the declared list the same way.

One more guard, because the spec list is a glob and yesterday's finding was a glob that could
match nothing: a test asserts there are specs to check at all, and another that every spec
declares both keys — otherwise a spec missing `capital_tiers` would make its parametrized case
pass without checking anything about it.

Sweep 2/2 on the sentinel.

## The dispatcher, its help text, and the Makefile

Two angles came back clean before this one, and both are worth recording so they are not
re-trodden:

**Ledger citation integrity — already handled, thoroughly.** I was going to check whether a row
could cite a deleted test. `check_ledger` already verifies that `code:` paths exist, that
**pytest collects** every cited test node, and it checks `building` rows too, with the reason
written down: *"a claim that goes unverified until someone promotes the row is a claim that rots
quietly in between."*

**Untested modules — a false positive from my own tool.** My first scan reported `a02`, `a03`
and `a04` as imported by no test. They are imported directly by `test_alpha_plugins.py`, whose
docstring describes them in detail; my regex did not handle `from … import a01, a02, a03, a04`.
Re-running with a proper AST parse of every import in `tests/` gave exactly one module.

### The finding

`pips.cli` was the only module under `python/pips/` that no test imported. It is a thin
if-chain, which is why it looked safe. But **three things name commands independently** — the
dispatcher that routes them, `_USAGE` which is what `pips --help` tells a person exists, and the
Makefile, which is the interface CLAUDE.md documents — and nothing held them together.

They had drifted. `provenance`, `s1-search` and `s5-smoke` were routed, invoked by `make`, and
absent from the help text. **`provenance` is a rung of `make ci`.** A command missing from the
help does not exist for anyone who has not read the Makefile or the source, and the help text is
a claim about the tool that was simply wrong.

### RED

```
FAILED test_every_routed_command_is_advertised
```

### What is pinned now

All three directions, plus the fallback that had never been tested: an unknown command exits 2
with a message on stderr (a quiet zero would let a typo'd Make target report success), `--help`
exits 0, and a bare invocation exits 1 — the two print the same text and must not share an exit
code, or a script that forgot its argument looks like one that asked for help.

The comparison parses the source rather than introspecting a registry, because there is no
registry, and building one to make the test prettier is a larger change than the finding
warrants. Running each command to find out whether it is routed is not an option either: that is
what `backfill` and `qc` do.

### My parser was wrong too, in the same family

The first version read the wrapped continuation of the `s1-search` entry as a command named
`successive`, and failed the advertised-but-unrouted test. A command entry has **exactly two
leading spaces** and a continuation has more, so keying on the indent is the real distinction in
the format — and it lets the help text wrap, rather than forbidding it to make my test pass.

Both of my mistakes this tick were the same shape as the defects I keep finding: a check whose
input was subtly not what I assumed. The difference is that these ones failed loudly.
