## Why "teach promotion the range shape" is the WRONG fix

That was the next unit named in CURRENT.md before this file existed, and it is wrong. It treats
the problem as a missing branch when it is a missing **layer**.

`_INTERVAL_MINUTES = 1`: silver is *definitionally* the one-minute intraday panel. Its bar model
is `(trade_date, close_label)` where the label is an intraday time clipped to the continuous
session. A daily bar has no intraday close label. Handling the range shape without addressing
that would walk every one of the 3,101 records into `normalize_candles`, clip every bar away,
and quarantine them all again — with `no bars survived normalization` instead of `KeyError`. A
worse message for the same outcome, and the appearance of progress.

There is a second reason it is the wrong frame: `normalize_candles` **ignores the candle's own
date** and stamps every bar with the single `trade_date` passed in. Any careless "explode the
range" patch would date three years of bars to one day.

## What is actually missing

Three things. **An earlier version of this card said only the first needed a decision. That
was wrong** — see the correction below the list.

1. **A home for daily bars.** Not specified anywhere in `IMPLEMENTATION.md` or the ledger. The
   plan in CURRENT.md says "rank on the three daily-derivable components" but never says where
   those bars live.
2. **A bars → `SymbolStats` path.** None exists: across the whole tree `SymbolStats(` is
   constructed only in tests. `liquidity_scores` is pure and takes them; `snapshot.py` receives
   them from a caller that does not exist.
3. **A three-component ranking that is not `liquidity_scores`.** `_usable` requires all four
   components, and spread is not derivable from daily OHLC at any interval. So the daily
   ranking must be its own function — calling `liquidity_scores` with spread missing is exactly
   what `_usable` refuses, and for a good reason it already states: *"a missing spread read as
   zero makes an illiquid name look tight"*.

### Correction, 2026-09-04: items 2 and 3 are not decision-free either

Checked before starting them, rather than after. The blueprint (§4.1) specifies the *score* —
`L = z(log median ₹-volume) − 0.75z(spread_bps) − 0.50z(Amihud) − 0.25z(gap_rate)` — and
`liquidity_scores` already implements exactly that. What it does **not** specify is how any
component is computed from bars.

- **`gap_rate` is undefined anywhere in this project.** It appears only as a field name and a
  weight (`-0.25` in `_WEIGHTS`). Nothing states what it measures — gaps above what threshold,
  over which sessions, measured against previous close or previous VWAP. Implementing it means
  inventing the semantics of a screen that decides which stocks are tradeable at all. **This is
  a second owner decision** and was not surfaced before.
- **Amihud must be PORTED, not written.** `salvage.yaml` carries `SAL-0015` (`decision: PORT`,
  `convexity a1ffbf145f97`, `src/convexity/cost/friction/validate/amihud_calibration.py`,
  7203 bytes, `covers_needs: ["M7 universe policy"]`). Verified reachable: the SHA resolves in
  `../past/convexity` and the file is exactly 7203 bytes. Constitution rule 13 makes writing a
  fresh implementation a violation, not a shortcut.
- **Median ₹-volume** is computable, but its lookback (20/40/60 sessions, "prefer median/lower
  quartile") is a *searched policy dimension* in the blueprint, not a constant to hardcode.

So the honest state is that no part of the daily ranking can be built right now without either
inventing semantics or skipping a salvage obligation. Recorded rather than worked around.

### A third consumer of the daily bars, found 2026-09-04

The instrument master cannot supply `sessions_listed`, and that turns out to matter more than
the 411 question it came from.

`/srv/pips/pit/instruments.jsonl` holds 5,851 rows and **every one has `valid_from:
1990-01-01` and `valid_to: null`**. So `InstrumentMaster.as_of` is a constant function — it
returned all 5,851 instruments at both edges of a three-year window. The master has no listing
history at all.

Follow that through M7:

1. Nothing can compute `EligibilityInputs.sessions_listed`, so it is `None`.
2. `eligible_on` records *"sessions_listed is unknown, so the warm-up cannot be checked"* as
   **undetermined** — correctly refusing to guess.
3. `eligible = not ineligible and not undetermined`, so undetermined means ineligible.
4. `snapshot.py` excludes it.

**Every instrument would be excluded and the universe would come out empty.** The code is right
at every step; the data is missing.

The fix is not another master download. `sessions_listed` is derivable from the daily bars —
count the sessions on which a symbol has one — which is exactly what the seed already holds.
That makes the daily bars the input to *eligibility* as well as to the ranking, and strengthens
the case for deciding where they live.

It also answers the 411: their `sessions_listed` is **0**, so they fall out as ineligible under
any warm-up (60/120/250). Not a data hole — the screen working. PANSTE's 8 bars likewise.

## The decision

**Option A — a daily panel beside silver.** Its own root and row shape (one row per
symbol-day, no intraday label), its own QC checks, its own promotion path. Silver keeps
meaning exactly one thing. Costs a parallel path; the two never share a bar model.

**Option B — silver gains an interval dimension.** One panel, rows keyed by interval, the
session clip applied only where an intraday label exists. Fewer concepts, but it changes the
meaning of every existing silver row and every reader of them, and `_INTERVAL_MINUTES = 1` is
currently load-bearing in ways that would need auditing one by one.

My read is **Option A**, because the daily bars exist for exactly one consumer — the liquidity
ranking that picks the 500 — and that consumer wants symbol-day rows, not minute bars. Option B
buys generality that nothing has asked for and puts the certified intraday panel at risk to get
it. But this changes the shape of M5/M6 either way, so it is the owner's call and not mine.

## What was NOT done

No code was written toward either option. Bronze is untouched — `Quarantined` records a reason
and moves nothing (§3.4). The 6 pre-existing day-keyed records promoted normally to 2,216 bars,
so the day-keyed path is confirmed working on real data.
