# BLK-0001 · M0.5: local Jenkins job cannot be created without credentials

```
milestone: M0.5        boundary: Jenkins (local, containerized)
escalated: human       opened: 2026-08-31        status: open
```

**symptom:** M0.5's second Verify — "Jenkins pipeline green on a scratch commit" — cannot be
executed. A Jenkins is running and reachable, but every API path returns
`Authentication required`, so no job can be created or triggered.

**repro:**
```
curl -s http://localhost:8080/api/json                 # -> 302 to /login, "Authentication required"
curl -s 'http://localhost:8080/api/json?tree=jobs[name]'  # -> empty
```

**expected vs actual:** expected an authenticated API able to create a `pips` pipeline job
pointed at this repo's root `Jenkinsfile`; actual is an anonymous-read-denied controller.

**tried:**
1. Anonymous REST read of `/api/json` and the job list — denied (auth required).
2. Looked for a `jenkins` CLI / brew service to read local config — none on PATH.
3. Inspected the running controller container for the prerequisites the `Jenkinsfile`
   needs — **these are satisfied**: `keeper-jenkins` (image `jenkins-jenkins`) has
   `/var/run/docker.sock` mounted and `/usr/local/bin/docker` present, so the pipeline's
   `docker build` + `docker run` stages will work once a job exists.

**why this is human-only, not a specialist dispatch:** the missing input is a *credential*
(a Jenkins user + API token). Constitution §2 / LOOP.md hard rails put credentials in the
human-only set — they are never to be simulated, guessed, or worked around. A §10.4
specialist agent would hit the identical wall on its first call.

**what the human needs to provide (precisely one of):**
- **(a)** A Jenkins API token for a user with Job/Create + Job/Build, exported on arb-vm/laptop
  as `JENKINS_URL`, `JENKINS_USER`, `JENKINS_TOKEN` (put them in a VM-side env file, never in
  git). With those, the next tick creates the job non-interactively and triggers a build.
- **(b)** Or: create the job by hand — *New Item → Pipeline → `pips`*, **Pipeline script from
  SCM**, SCM = Git, repo = this checkout, branch spec `*/main` plus `*/m/*`, script path
  `Jenkinsfile` — and say so on this card. The next tick then only needs to trigger it.

Note this controller currently serves the `keeper` project. If `pips` should have its own
controller rather than share one, say so here and the next tick stands one up in compose
instead (that path needs no credential from the existing instance).

**relevant shards:** `[C-DEPLOY-01]` (building), `[G-DEPLOY-01]` (planned, M3.5);
ADR-0007 (native Jenkins, no GitHub Actions); root `Jenkinsfile`; IMPLEMENTATION.md §2.2.

**danger notes:** the specialist/next tick must NOT touch the existing `keeper` jobs or the
controller's global security config; must not put any token in git or in an image; must not
enable any live flag. Read-only probing of the controller is fine.

**blast radius while open:** none for research work. M1–M2 proceed on `docker compose run
research make ci`, which is green. What is lost is the *merge gate* — until Jenkins runs the
ladder, "green CI" is asserted by the containerized run rather than certified by CI.
