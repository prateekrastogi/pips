# BLK-0002 — the pre-push gate cannot run: Docker Desktop is stopped

**Opened:** 2026-09-01 · **Status:** RESOLVED same day (option 1)
**Blocks:** pushing `3913df0` (M19 netting + fixed point). Nothing else.

## What happened

`git push` was refused by the pre-push hook. The hook runs `pips-ci` on the local Jenkins at
`127.0.0.1:8081`; that connection is refused, because Jenkins runs as a Docker Compose service
and **Docker Desktop is not running** (`docker info` fails, no `Docker Desktop` process, the
socket at `~/.docker/run/docker.sock` does not exist).

This is not a red build. The gate could not run at all.

## Why this is the owner's call rather than mine

The hook itself sanctions the bypass for exactly this case — *"if you must push anyway (e.g. …
the controller itself is down), use `git push --no-verify` and record why"* — so the constitution
already contemplates it and rule 10 is not at stake.

What makes it a decision rather than a default: starting Docker Desktop means starting a Linux
VM plus the Jenkins controller and rebuilding the research image. That is multiple GB of real
memory, and the owner raised resource usage on this machine minutes before this block opened.
Spending it silently on their behalf is not mine to do.

## What is and is not verified

Verified locally on the working tree, all green:

| check | result |
|---|---|
| `ruff check` + `ruff format --check` | clean, 199 files |
| `mypy --strict` | clean, 199 files |
| `pytest` | 1189 passed |
| `ledger check` | 30 rows |
| mutation run | 24 of 24 |

NOT verified: that this builds and passes **from a clean checkout of the pushed SHA**, which is
the specific thing Jenkins adds and which CLAUDE.md records as having caught two failures a
local green missed. That gap is the entire cost of the bypass.

## Options

1. **Start Docker + Jenkins** (`make jenkins-up`, then push normally). Full gate, costs the
   memory.
2. **`git push --no-verify`**, with this card and a log entry as the required trace. The clean
   checkout goes unverified until the next gated push, which would cover it.
3. **Leave `3913df0` unpushed** until Docker is up for other reasons. Costs nothing; the work
   sits local and arb-vm's deploy rail does not see it.

## Note

`[G-PROV-01]` is unaffected — it refuses a stale image, which is a different failure from no
image at all. The `make ci-container` path is equally unavailable while Docker is down, so the
laptop currently has no containerised verification either.

## Resolution

Owner chose option 1. Docker Desktop started (daemon up in ~10s, 29.7.2), `make jenkins-up`
recreated `pips-jenkins` and it answered on `127.0.0.1:8081` in ~10s. `git push` then ran the
gate normally: **pips-ci #106 SUCCESS**, pushed on green, and arb-vm's deploy rail took
`56e196e423e1`.

So the clean-checkout gap the card describes was never taken — the bypass was not used and the
pushed SHA is verified from a fresh checkout, not just locally.

**Standing note for future ticks:** this block is environmental, not a defect. It reopens
whenever Docker Desktop is not running, and the tell is a *connection refused* on 8081 rather
than a red build. Distinguish the two before reaching for `--no-verify`: a red build means fix
the code, an unreachable controller means start it. Docker and Jenkins hold real memory while
up; `make jenkins-down` and quitting Docker Desktop releases it when a session is not pushing.
