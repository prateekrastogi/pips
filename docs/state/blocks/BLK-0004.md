# BLK-0004 — Breeze accepts our REST calls and refuses our streaming namespace

**Opened:** 2026-09-04 · **Status:** OPEN — owner answered; the stated causes are RULED OUT and
the symptom is now unexplained. Next test is Monday's session.
**Blocks:** forward capture (`pips capture --live`) and everything that needs a live tape —
spread measurement, and therefore the fourth component of the liquidity score. Does **not**
block historical backfill, which is working.

Recorded because it had no card. It was diagnosed hours ago and lived only in a dead
container's logs, which is exactly how a human-only item gets quietly forgotten.

## What happens

`pips capture --symbols … --live` on arb-vm, container `pips-capture-20260904`, exited 1:

```
File ".../breeze_connect.py", line 211, in _ws_connect
    self.sio_rate_refresh_handler.connect(config.LIVE_STREAM_URL)
File ".../breeze_connect.py", line 86, in connect
    raise Exception(except_message.LIVESTREAM_SOCKET_CONNECTION_DISCONNECTED.value)
Exception: Failed to connect to live stream

socketio.exceptions.ConnectionError: One or more namespaces failed to connect:
```

Note the message ends with an empty list — the library names no namespace.

## What has been ruled out, by measurement rather than by argument

All from arb-vm, 2026-09-04:

| checked | result | rules out |
|---|---|---|
| DNS for `livestream.icicidirect.com` | resolves (CloudFront) | name resolution |
| TCP 443 to that host | reachable | egress/firewall |
| `GET /socket.io/?EIO=4&transport=polling` | **HTTP 200** | the endpoint being down |
| the handshake body | `{"sid":"…","upgrades":["websocket"],"pingInterval":25000,…}` | Engine.IO layer |
| Breeze REST with the same session token | Status 200, and the daily seed fetched 2,690 symbols with it | the token, the API key, the account |

So the transport completes, a session id is issued, and a websocket upgrade is offered. The
failure is specifically the **authenticated Socket.IO namespace connect**. The server is
refusing the namespace, not failing to be reached.

Our own code has been eliminated too: `feed.close()` was raising `BadNamespaceError` from
`run_capture`'s `finally` and masking this exact error. Fixed the same day — `close()` now
records `close_error` instead of throwing — so the trace above is the real one, not the mask.

## The question for ICICI / Breeze support

> Our API key completes the Engine.IO handshake against `livestream.icicidirect.com`
> (session id issued, websocket upgrade offered) but the authenticated Socket.IO namespace
> connect is refused, and `breeze_connect` reports "Failed to connect to live stream". REST
> historical calls with the same session token succeed (Status 200). **Is the streaming /
> live-feed entitlement enabled for this API key, and does it require a separate activation
> or a registered static IP?**

The API key and session token live in the git-tracked `.env` per ADR-0011. **Neither belongs in
a support ticket**; quote the key only if ICICI asks, and never the session token, which is a
live credential that rotates daily.

## Why this is human-only

Rule 7 keeps the data plane's credentials separate from the order plane's, and no amount of
code changes an entitlement. LOOP.md's hard rail: human-only items are recorded precisely and
held, never simulated. There is no code change that would make this connect, and any retry loop
would just be a slower way of getting the same refusal.

| question | answer |

So the two things this card proposed as causes are not the causes. Every hypothesis it and I
raised is now eliminated:

| ruled out | how |
|---|---|
| entitlement not enabled | owner: enabled |
| arb-vm not whitelisted for streaming | owner: whitelisted for both |

**The failure is therefore unexplained, not diagnosed.** That is a worse position than this card
described yesterday, and it should be said plainly rather than left looking answered. Two
hypotheses survive, neither testable before a live session:

1. a transient vendor-side fault on 2026-09-04 that may simply not recur;
2. something in `breeze_connect`'s `ws_connect` flow itself — the SDK reports
   `"One or more namespaces failed to connect: "` with an EMPTY namespace list, which is the
   library declining to say what it could not connect to.
